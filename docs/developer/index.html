Architecture

One Rust binary, one Elixir server, one graph per repository. Full text: ARCHITECTURE.md.

The problem it solves

A Claude Code session ends or compacts, and the reasoning goes with it: which option lost and why, what was tried, what the user asked for in their own words. Deciduous keeps that as a graph the next session can query, and since 1.1.0 can rebuild the graph from the session's transcript when the agent did not log.

Where the graph lives is chosen at init. With a [remote] in .deciduous/config.toml (the default since 1.0.5; since 1.0.11 a server on this machine against the PostgreSQL on localhost:5432), the server is the truth and the SQLite file is a cache: CLI writes go to the cache, are logged as ops in remote-log.jsonl, and are sent before the command exits; MCP writes reach the cache on remote pull. Without a [remote], graph.json is tracked by git, deciduous sync reconciles it with the database in both directions, and the deciduous merge-record driver (hidden from --help, registered by init) merges concurrent edits record by record. remote-graph.md and MULTI_USER_SYNC.md are the two models in full.

There is no hooks layer. Up to 1.0.2 a hook denied the agent's next tool call until it logged; 1.0.3 removed it. init installs two hooks that never block: a once-a-day version check and board-mentions.sh, which shows a session with DECIDUOUS_AGENT_LABEL its unanswered board messages. What tells the agent when to log is the shared server's instructions on initialize and the CLAUDE.md section; what catches what it did not log is the transcript import.

Node types

TypePurposeExample
goalWhat was asked for; the prompt verbatim in metadata.prompt"Add rate limiting to the public API"
optionAn approach considered"Token bucket in Redis"
decisionThe option chosen, named against what it beat"Token bucket in Redis, over the fixed window"
actionCode or config changed; files and commit in metadata"Implement RateLimiter middleware"
outcomeWhat happened: the number or the error"cargo test: 41 passed, 0 failed"
observationA fact that changes the plan"Redis failover drops bucket state"
revisitAn earlier choice reconsidered; connects old to new"Reconsidering: Token bucket in Redis"

Edge types: leads_to, requires, chosen, rejected, blocks, enables, took_from. Statuses: pending, active, completed, rejected, superseded, abandoned. Every node has a local integer id and a change_id UUID that is the same on every machine.

Concepts

How to think about the graph. Full text: CONCEPTS.md and narratives.md.

Log before, not after

action   ← what is about to change, and in which files
outcome  ← what happened: "212 passed, 0 failed", or the error
link     ← in the same breath, to the parent

An outcome written after the fact tends to be an adjective ("working"). One written from the test run is a number, and a number can be checked later. The transcript import applies the same rule mechanically: a cargo test result is an outcome marked proven; the assistant's "all tests pass" is marked inferred, next to it.

Options before decisions

A goal does not lead straight to a decision. The options come first, with chosen and rejected edges into the decision that carry the reasons. The rejected option is the part you will want back in six months, and it is the part a summary drops.

The pivot

[decision: Token bucket in Redis] (superseded)
      │
      ▼
[observation: Redis failover drops bucket state]
      │
      ▼
[revisit: Reconsidering: Token bucket in Redis]
      │
      ▼
[decision: Fixed window counter in Postgres, 60s windows]

deciduous archaeology pivot OLD "observation" "new approach" writes the three nodes and three edges and marks the old decision superseded, atomically; --dry-run shows the plan. The old decision stays: deleting it would delete the reason the new one exists. deciduous narratives pivots reads every pivot chain back.

The prompt field

# A summary loses the request
deciduous add goal "Add auth" -p "User wants login"

# The user's words survive compaction
deciduous add goal "Add auth" --prompt-stdin << 'EOF'
I need to add user authentication to the app. Users should be able to sign up
with email/password, and we need OAuth support for Google and GitHub.
EOF

The CLI warns when a prompt is short enough to look like a summary; the node is created either way. The transcript import stores every prompt verbatim without being asked.

Evidence

Nodes derived from a transcript carry metadata.evidence: kind is proven (a tool call and its result, or the user's own words, with the entry uuids and tool_use ids) or inferred (the assistant said so). Actions carry metadata.consulted, the files read since the previous action, and metadata.file_hashes, git blob ids of the files touched. deciduous show prints them; the web viewer does not yet. Full text: transcripts.md.

Sharing

Two models, chosen at init. With a [remote]: one PostgreSQL holds every project's graph, one workspace per repository; the CLI's writes are ops replayed on the server; agents write through the server's MCP tools; deciduous remote status compares the cache with the server field by field. Without one: .deciduous/graph.json is the shared file, carried by git, reconciled by deciduous sync and merged record by record by the merge-record driver. The 0.17 per-record directory .deciduous/sync/ and the earlier diff export / diff apply patches are gone; a 0.17 directory is folded into graph.json by the next sync.

Coordination is not the graph

Agents working at the same time talk on the message board (deciduous board, post_message / read_messages): interface changes, questions, answers, with ids and replies. Messages are never in graph.json, never exported, never synced. Locally the board is the main worktree's database, shared by every worktree; with a [remote] it is on the server.

Web Viewer

deciduous serve. Full text: WEB_VIEWER.md.

deciduous serve                # http://localhost:3000, this project's database
deciduous serve --port 8080

Six views: DAG, Chains, Timeline, Graph, Roadmap, Story. The viewer is a React/TypeScript app in web/, built to a single HTML file and embedded in the binary as src/viewer.html; after changing web/src/**, cd web && npm run build and copy web/dist/index.html over src/viewer.html and docs/demo/index.html. The live demo on this site is that build reading docs/graph-data.json, which was last exported on 2026-09-04; deciduous sync has not written it since 1.0.5.

Routes the server answers

RouteReturns
GET /api/graphnodes and edges
GET /api/commandsthe command log
GET /api/git-historycommits for nodes that carry a hash
GET /api/roadmap, POST /api/roadmap/checkboxROADMAP.md items; toggle one
POST /api/aska question answered by the claude CLI with graph context; stored, and searchable with GET /api/qa/search?q=

Chain building

web/src/utils/graphProcessing.ts builds chains by BFS over whole connected components, following outgoing and incoming edges, with no node cap, so one chain is the entire tree a goal belongs to. The viewer embedded in the binary draws a took_from edge as a plain line; the source draws it dash-dot (CHANGELOG 1.0.0).

The other server mode

deciduous serve --api --data-dir DIR --token T [--bind 127.0.0.1] is not the viewer: it is the 0.16 multi-graph JSON API daemon, one SQLite file per graph under DIR/graphs/<id>/, bearer-token auth, append-and-read only (DECIDUOUS_API_DATA_DIR and DECIDUOUS_API_TOKEN answer for scripts). The shared graph server in deciduous_mcp/ superseded it as the way to share a graph; the daemon remains in the binary.

Quick Reference

Every command here is in 1.1.0's --help. Full text: QUICK_REFERENCE.md; the walkthrough is the guide.

Set up

deciduous init [--claude|--opencode|--windsurf|--both]   # writes the files, then asks where the graph lives
deciduous remote setup --local | --database-url URL | --docker-postgres | --url URL   # the same answer, for scripts
deciduous update [--all DIR]                            # replace what deciduous wrote; keep what you edited
deciduous check-update                                  # exit 1 if integration files are behind the binary

Write

deciduous add goal "Title" -c 90 --prompt-stdin << 'EOF'
the user's message
EOF
deciduous add option "A" ; deciduous add option "B"
deciduous add decision "A, over B" -c 85
deciduous link GOAL A -r "possible approach" ; deciduous link GOAL B -r "possible approach"
deciduous link A DECISION -t chosen -r "why" ; deciduous link B DECISION -t rejected -r "why not"
deciduous add action "What changes" -c 85 -f "src/a.rs,src/b.rs"
deciduous add outcome "212 passed, 0 failed" -c 95 --commit HEAD
deciduous add observation "Title" -d "what was seen and what it implies"
deciduous status ID completed|superseded|abandoned|active|pending|rejected
deciduous archaeology pivot OLD "observation" "new approach" -c 80 -r "why" [--dry-run]
deciduous transcript import SESSION_ID [--dry-run] [--no-hash]

Read

deciduous nodes [-b BRANCH] [-t TYPE] [--theme NAME]
deciduous edges
deciduous show ID [--json]
deciduous pulse [--summary]
deciduous commands
deciduous archaeology timeline [-l N]
deciduous narratives pivots
deciduous transcript list
deciduous graph                      # everything, JSON

Output

deciduous serve [-p 3000]
deciduous dot --png --auto           # docs/decision-graph-<branch>.png (needs Graphviz)
deciduous writeup -t "Title" -n 1-9 [--auto]
deciduous doc attach ID FILE [-d "..."] ; doc list [ID] ; doc show ; doc open ; doc detach ; doc gc
deciduous board post --as LABEL -s "subject" -m "@other body" ; board read --unanswered LABEL ; board show ID

Share

# with a [remote]
deciduous remote status              # cache vs server, field by field; exit 1 on any difference
deciduous remote pull                # take the server's side
deciduous remote push [--seed]       # send the queued ops; --seed sends history that predates the server
deciduous remote watch               # one line per write, live

# without a [remote]
deciduous sync                       # reconcile .deciduous/graph.json with the database
deciduous sync --check               # exit 1 if anything is pending
git add .deciduous/graph.json        # by path, never git add -A

Environment variables the binary reads

VariableEffect
DECIDUOUS_MCP_TOKENThe server token; overrides the credentials file. Never written to config.
DECIDUOUS_DB_PATHThe database to use instead of walking up to .deciduous/; for Claude Desktop and worktrees.
DECIDUOUS_PORTThe port for this machine's server, the first time it is set up.
DECIDUOUS_NO_SERVERSkip init's server step (tests, CI).
DECIDUOUS_QUIET_LOCAL_ONLYSilence the stderr line a write prints when the project has no server anywhere.
DECIDUOUS_OPS_TIMEOUTPer-request timeout when replaying ops to the server.
DECIDUOUS_AGENT_LABELThis session's board label; board post --as default and the board-mentions hook.
DECIDUOUS_API_DATA_DIR, DECIDUOUS_API_TOKENserve --api settings.
DECIDUOUS_BIND_ADDRESSIn ~/.config/deciduous/server/.env: the address this machine's server listens on (setup writes 127.0.0.1).

DECIDUOUS_ENV_FILE, DECIDUOUS_SERVER_MODE and DECIDUOUS_MCP_INSTALL_DIR also exist in the source, for the server install; they are not documented here because their behaviour was not verified for this page.
