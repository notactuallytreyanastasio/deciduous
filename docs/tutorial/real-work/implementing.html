The Implementation Session

Claude writes the code, logs the action first, commits, and links the outcome to the commit. Then its context compacts and /recover gets it back from the graph.

Chain: goal #16 → option #17 → decision #19 → action #20 → outcome #21, with the commit on the outcome. The integration workflow is next.

-f and --commit HEAD

-f on the action records which files the work intends to touch; --commit HEAD on the outcome records the commit that contains the result, resolved to its full hash. Together they are the audit trail: what was planned, what changed, which commit. The web viewer shows the commit message, author and date beside the node.

The graph held everything Claude needed: the original request on the goal, the chosen approach, what is done, what remains. The edges are the recovery path; an unconnected node tells a recovering session nothing about why it exists.

Do not let a compacted session stumble on

When answers stop referring to what came before, run /clear and then /recover with one line about where you were: /recover — integration workflow next, node 21 is done. A fresh context recovered from the graph does better than a degraded one.

The command log

/recover's last step reads deciduous commands, the recent command log. In the scratch project for this tutorial it printed No commands logged. after thirty-odd commands; do not count on it for recovery. The graph and the transcript are what carry the context.
