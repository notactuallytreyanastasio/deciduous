Building a Graph from Git History

Point your assistant at a repository with /decision-graph. It reads every commit, finds the eras and the pivots, and writes backdated nodes grounded in real commits.

What the Command Tells Claude

The .claude/commands/decision-graph.md file that init wrote is a set of instructions, and the first of them is the one that keeps the result honest: only use information from the repository itself (commits, code, comments, tests); do not use prior knowledge about the project. Then a layered search: see all commits first (never git log | head -100, which drops the middle), expand keywords once narratives emerge ("cache" to "caching", "LRU", "invalidate"), follow key authors a month either side, and read PR descriptions with gh pr view because reviewers surface the alternatives that never reach commit messages. The temporal rule says that options under a decision are alternatives considered at the same time; an approach that was tried, failed and replaced years later is a new decision reached through observations, not a sibling option.

Here it is on snowflex. The scratch repository used for this tutorial has three commits standing in for the history; the ids and output are real.

Under the Hood

Dates and commits

--date 2019-06-15 sets created_at, so the timeline and the viewer place the node where the history puts it, not where today is. --commit da7ef84 takes a hash, a prefix, HEAD, a branch or a tag; it is resolved with git rev-parse and stored as the full hash, which is why the output shows forty characters. A rev git cannot resolve is refused and nothing is written:

$ deciduous add outcome "..." -c 90 --commit nosuchrev
Error: --commit: "nosuchrev" is not a commit in this repository (git rev-parse could not resolve it). Nothing was written.

Edges and their direction

Every deciduous link FROM TO is a directed edge, leads_to unless -t says otherwise, with -r for the rationale. The option that won points at the decision with chosen; the decision points at the option it dropped with rejected. Why not also draw the decision pointing back at the chosen option? Because the two nodes would become each other's parent, and the binary refuses that:

$ deciduous link 4 2 -t chosen -r "trying the reverse direction"
Error: 2 -> 4 (chosen) already exists; 4 -> 2 would make the two nodes each other's parent. A decision's options hang under it (decision -> option); to put a decision under its goal, link goal -> decision.

A 2-cycle breaks every traversal that asks "what led to this?", so link refuses it, and since 1.0.11 sync refuses the same thing arriving in a hand-edited graph.json.

Confidence and status

-c 90 is how sure the author is, 0 to 100; pulse buckets it as high, medium, low or unset. Nodes the CLI creates start with status pending. Setting active, completed, rejected, superseded or abandoned is a separate deciduous status call, which the next page shows.
