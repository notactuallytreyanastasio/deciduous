Telling the Story with Narratives

The graph captures structure. Narratives capture the human-readable story.

A decision graph with 56 nodes and 66 edges is a powerful data structure, but it's not something you hand to a new team member and say "read this." Narratives are the layer on top—prose documents that explain the evolution of a system in plain language, grounded in the graph's structure.

Initializing Narratives

The deciduous narratives init command scaffolds a narrative document based on the active goals in your graph:

deciduous narratives init
deciduous narratives init Created .deciduous/narratives.md with 3 active goal titles: - Create an Elixir library for querying Snowflake - Transport layer evolution - Authentication and key management

This creates .deciduous/narratives.md with section headers pulled from your goal nodes. The file is a starting point—you or Claude fill in the evolution story for each section.

For snowflex, the scaffolded file looks like this:

.deciduous/narratives.md (scaffolded)
# Snowflex Narratives ## Create an Elixir library for querying Snowflake ## Transport layer evolution ## Authentication and key management

Claude typically fills these in during the archaeology session, drawing on the commit history and the graph nodes it just created. The result is a prose document that reads like a project history, with references back to specific graph nodes for anyone who wants to dig deeper.

Viewing Narratives

Once narratives are written, view them from the CLI:

deciduous narratives show
deciduous narratives show # Snowflex Narratives ## Create an Elixir library for querying Snowflake Snowflex started in June 2019 as a thin wrapper around Erlang's ODBC driver. The goal was simple: give Elixir applications a way to query Snowflake data warehouses. At the time, there was no Elixir library for Snowflake, and the Erlang ODBC driver was the only viable bridge. The first version (nodes #1-5) was a single-connection wrapper. It worked, but couldn't handle concurrent queries. This led to the ConnectionPool era (nodes #6-9), which added a supervision tree for managing multiple ODBC connections. The pool worked but the API was cumbersome (node #10). The module-based API era (nodes #11-14) replaced the pool with a pattern modeled after Ecto.Repo, using Elixir's __using__ macro. This was the API that stuck through v0.2-v0.8. ## Transport layer evolution The ODBC driver served snowflex for two years, but problems accumulated: session expiry after 4 hours idle (node #15), UTF-16 encoding corruption (node #22), Apple Silicon incompatibility, and memory issues (node #33). The pivot came in early 2021 (node #34). The team evaluated two approaches: a transport behavior with HTTP implementation using Req (node #37, chosen), and a direct HTTP client without abstraction (node #38, rejected). The transport behavior won because it allowed future extensibility. The v1.0 rewrite (node #39) replaced ODBC entirely with HTTP REST APIs and JWT authentication. The result (node #40) was a modern, portable Snowflake adapter with no native dependencies. ## Authentication and key management ...

The narrative references specific node IDs so readers can cross-reference with the graph. This is intentional—the narrative is the story, the graph is the evidence.

Finding Pivot Points

The narratives pivots command extracts every revisit node and shows the chain of events that led to each pivot:

deciduous narratives pivots
deciduous narratives pivots Pivot chains: #34: Reconsider ODBC as transport - switch to HTTP REST API 32 (outcome) → 33 (observation) → 34 (revisit) → 36 (decision) Reason: ODBC too fragile for production #46: Reconsider single-key auth - support multiple key formats 44 (outcome) → 45 (observation) → 46 (revisit) → 48 (decision) Reason: Enterprise customers need key rotation

Each pivot chain traces the path from an old outcome, through the observation that revealed the problem, through the revisit that reconsidered the approach, to the new decision that replaced it. These are the most architecturally significant moments in any project, and this command surfaces them instantly.

Archaeology Timeline

For a chronological view of the entire project history as captured in the graph, use archaeology timeline:

deciduous archaeology timeline
deciduous archaeology timeline --limit 15 Timeline (15 of 56 nodes): 2019-06-15 #1 goal Create an Elixir library for querying Snowflake 2019-06-15 #2 option Use Erlang ODBC driver to connect to Snowflake 2019-06-20 #3 decision How to connect Elixir to Snowflake? 2019-06-25 #4 action Implement initial ODBC wrapper with single connection 2019-07-01 #5 outcome Working single-connection ODBC wrapper 2019-08-15 #6 decision How to support multiple Snowflake connections? 2019-08-15 #7 option Explicit ConnectionPool in supervision tree 2019-09-01 #8 action Implement ConnectionPool-based multi-connection support 2019-09-15 #9 outcome Multi-connection support via ConnectionPool (v0.1) 2019-10-01 #10 observation ConnectionPool API is cumbersome vs Ecto.Repo pattern 2019-11-01 #11 decision How to improve connection API ergonomics? 2019-11-01 #12 option Module-based connection using __using__ macro 2019-12-01 #13 action Replace ConnectionPool with module-based Connection 2020-01-01 #14 outcome Ergonomic module-based connection API (v0.2) 2020-01-15 #15 observation Snowflake ODBC sessions expire after 4 hours idle

Filter the timeline to show only specific node types:

Filtered timeline
deciduous archaeology timeline --node-type revisit Timeline (2 of 56 nodes, filtered to: revisit): 2021-03-15 #34 revisit Reconsider ODBC as transport - switch to HTTP REST API 2021-08-01 #46 revisit Reconsider single-key auth - support multiple key formats

The timeline gives you the "when" that complements the graph's "what" and "why." Combined with narratives and pivot chains, you have a complete picture of a project's evolution.

Two audiences, two formats

Narratives bridge the gap between the structured graph and human understanding. The graph is for machines to query; narratives are for humans to read. Use the graph when you need precision and traceability. Use narratives when you need to onboard a teammate or write a design document.
