What is Deciduous and Why Should I Care?

Three months into a project someone asks why you chose PostgreSQL over MongoDB. There was a reason, something about transactions and the data model, but the Claude session where you worked it through has long been compacted and the Slack thread is buried. You say "it made sense at the time."

That is the problem deciduous is built against, and it has got worse with AI-assisted development: an assistant considers three approaches, rejects two, implements one, and the reasoning is gone when the context window compacts or the session ends.

What a Decision Graph Is

One graph per repository. Its nodes are of seven types: goal, option, decision, action, outcome, observation and revisit. Its edges are leads_to, requires, chosen, rejected, blocks, enables and took_from. The canonical flow is:

goal → options → decision → actions → outcomes

A goal leads to the options considered; the options lead to the decision that picked one; the decision leads to the actions that implemented it; the actions lead to what happened. Observations attach wherever they were made. A revisit marks the moment an earlier approach was reconsidered. Every node has a status, and nodes created by the CLI start as pending.

Three Ways the Graph Gets Written

  1. The CLI. deciduous add goal "...", deciduous link 1 2, and the rest. This is what the tutorial shows, because its output is easy to read.
  2. MCP tools, while the agent works. There are two servers. deciduous mcp is a local stdio server with 34 tools (add_node, link_nodes, search_nodes, trace_chain, ...). The shared graph server, which deciduous init sets up and registers with Claude Code, speaks MCP over HTTP with 21 tools (add_node, capture_conversation_turn, ask_graph, query_nodes, post_message, ...). When Claude Code connects to it, the server sends the logging instructions; no hook is involved.
  3. The transcript, after the fact. New in 1.1.0: deciduous transcript import reads the JSONL file Claude Code writes for every session and derives goals from your prompts, actions from edits and commits, and outcomes from test runs. Every derived node says whether it is proven (a tool call and its result) or inferred (the assistant said so). Importing a Transcript shows it on a real session.

The third one changes the premise. An agent that logs its own decisions can forget to; the transcript cannot. On a three-week session that had logged nine nodes through MCP, the import found 119 actions, 67 command outcomes and 68 verbatim prompts.

Where the Graph Lives

Since 1.0.11, deciduous init asks. The default is a server on this machine, installed as a user service (launchd on macOS, systemd on Linux) against the PostgreSQL already on localhost:5432. The alternatives are a PostgreSQL you name, a new PostgreSQL and server in Docker, or a server someone else runs. The server is the truth; .deciduous/deciduous.db, the SQLite file in your checkout, is this machine's cache of it. Every project on the machine shares the one server, one workspace per repository, and the shared server's ask_graph can search across all of them.

A project that never answered that question (tests and CI set DECIDUOUS_NO_SERVER=1) keeps the older model: the SQLite file is the graph and .deciduous/graph.json, committed to git and merged record by record by a merge driver, is how it travels between clones.

The Story We'll Follow

snowflex connects Elixir to Snowflake. It started as one module around Erlang's ODBC driver. Over about 130 commits it grew a connection pool, then a module-based API modelled on Ecto.Repo, then threw the ODBC transport away for Snowflake's HTTP REST API with JWT authentication, then made key management flexible. Each pivot was driven by production pain. You will reconstruct that history as a graph, then work a real open issue (#93, CI pipelines) with Claude logging as it goes.

Two Ways to Use It

Archaeology: an existing project
> /decision-graph I'll read the full commit history first, then map the eras. git log --oneline --reverse | wc -l 130 deciduous add goal "Create an Elixir library for querying Snowflake" -c 100 --date 2019-06-15 --commit da7ef84 Created node 1 (type: goal, title: Create an Elixir library for querying Snowflake) [confidence: 100%] [commit: da7ef84427ca8625acc0dccfd88cda1c86566d3d] [branch: main] [date: 2019-06-15T00:00:00-04:00]
Forward logging: new work
> /work Add CI pipelines for snowflex (issue #93) Logging the goal with your request verbatim before touching anything. deciduous add goal "Add CI pipelines for snowflex" -c 90 --prompt-stdin << 'EOF' Add support for running tests in CI/CD. We need GitHub Actions workflows for both unit tests and integration tests. See issue #93. EOF Created node 16 (type: goal, title: Add CI pipelines for snowflex) [confidence: 90%] [prompt: 130 chars] [branch: ci-pipelines]

In a Claude Code session connected to the server, the agent makes the same writes through MCP (add_node with parent_id, one call per node and edge) rather than the shell. The graph is identical either way.

What You Get

  • Context that survives. /recover at session start reads the graph, imports any transcript the graph does not have yet, and checks the message board.
  • Questions answered from evidence. Ask "why did we drop ODBC?" and the assistant answers from the revisit node and the observations behind it.
  • PRs that explain themselves. deciduous writeup and deciduous dot --png produce the PR body and the picture.
  • Several agents, one graph. Parallel sessions write to the same workspace and coordinate on the message board (deciduous board).

Deciduous tracks its own development this way. The graph exported with this repository held 1,465 nodes and 1,313 edges on 2026-10-24.

Why "Deciduous"?

Deciduous trees shed their leaves; the structure stays. The working memory of a session falls away, and the graph remains for the next one.
