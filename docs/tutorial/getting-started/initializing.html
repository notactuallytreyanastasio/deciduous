Initializing on a Project

deciduous init writes the files your assistant reads, then asks one question it will not guess the answer to: where should this project's graph live?

Everything above the menu was run for this tutorial; the menu is the text init prints when the project has no [remote] yet (the scratch run set DECIDUOUS_NO_SERVER=1, and printed Skipped shared graph server there instead). If nothing answers on 5432, the first line reads nothing answers there now and a hint under the menu names the brew and apt commands.

The Four Answers

  1. This machine, PostgreSQL on 5432 (default). The first time on a machine, init downloads the server executable for its own version, checks it against the release's checksums.txt, runs it once to create the database deciduous and migrate, then installs it under ~/.config/deciduous/server/ as a user service that starts at login (a LaunchAgent on macOS, a systemd user unit on Linux), listening on 127.0.0.1 only. It asks for a port and suggests a free one from 20000-32767; 4000 is not assumed because it is Phoenix's default and would break the dev server of the very project being logged. If PostgreSQL refuses (no such role, no CREATEDB), you see its reason and the menu again.
  2. This machine, a PostgreSQL you name. Same server, a URL of the form postgres://USER@HOST:PORT/DATABASE; the password is asked separately and never shown.
  3. Docker. A new PostgreSQL 17 and the server in containers. This is what 1.0.10 and earlier always did.
  4. Someone else's server. URL and token, both checked before anything is stored.

Whichever you pick, init stores the token in ~/.config/deciduous/credentials (mode 0600, outside every repository), writes [remote] with the URL and this repository's workspace name to .deciduous/config.toml, and registers the server with Claude Code (claude mcp add --scope user --transport http deciduous <url>/mcp --header "Authorization: Bearer $DECIDUOUS_MCP_TOKEN", run for you). The second project on the machine finds the running server in about a second and skips all of this.

In a script there is no terminal to ask, so answer on the command line
deciduous remote setup --local # 1 deciduous remote setup --database-url <url> # 2 deciduous remote setup --docker-postgres # 3 deciduous remote setup --url <url> # 4 DECIDUOUS_NO_SERVER=1 deciduous init # tests and CI: skip the step

Then restart Claude Code. When it connects to the server, the server sends the logging instructions. There is no hook to install.

# Deciduous: local database stays private, the shared graph is tracked

Note what that rule covers: the database, .deciduous/documents/, .deciduous/remote-log.jsonl (unsent writes to the server), narratives.md and backups all stay out of git. init no longer writes a docs/ viewer or a GitHub Pages workflow; that stopped in 1.0.5, when the graph moved to the server and deciduous serve became the way to look at it.

Run deciduous update to update integration files.

It exits 1 when an update is needed, 0 otherwise, so it works in a script. Then:

deciduous update, after someone edited a heading inside the CLAUDE.md section
deciduous update Updating Deciduous tooling for Claude Code... Directory: /Users/alice/code/snowflex Unchanged .claude/commands/decision.md Unchanged .claude/commands/recover.md ... Unchanged .claude/skills/archaeology.md Kept yours CLAUDE.md (its deciduous section was edited by someone and is left as it is; the section it would have got: .deciduous/update-templates/CLAUDE.md) Updated .deciduous/.version (1.1.0) Tooling updated for Claude Code!
Since 1.0.12, update keeps what you wrote

A file deciduous wrote is replaced; a file or section someone else edited is kept, and the text it would have written goes to .deciduous/update-templates/<path> so you can diff it. Everything update does change is copied first to .deciduous/update-backups/<unix-time>/. A second update is a no-op. In 1.0.3 through 1.0.11 an edited section on a project with a [remote] was rewritten back to the git model and could end up with a doubled start marker; that is the bug 1.0.12 fixed.

update also removes the logging hooks that versions before 1.0.3 installed, asks the server question if the project still has no [remote], and upgrades this machine's server executable when it is older than the CLI. It never touches .deciduous/config.toml.

auto-update is a no-op

init --no-auto-update is still accepted and silently ignored. deciduous auto-update on|off still exists and prints a note that version checking is always on: once per 24 hours, non-blocking, through the version-check.sh hook. There is no setting behind either.
