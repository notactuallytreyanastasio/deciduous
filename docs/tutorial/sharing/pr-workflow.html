The PR Workflow

The PR body comes from the graph, the picture comes from the graph, and the teammate who reviews it usually has nothing to import: with a graph server, the nodes were theirs the moment they were written.

Step 1: The Picture

$ deciduous dot --auto --nodes 16-21 --title "CI pipeline decisions"
Exported DOT: docs/decision-graph-ci-pipelines.dot
Generated PNG: docs/decision-graph-ci-pipelines.png

--auto names the files after the branch, so two branches each carrying a graph image do not conflict at merge. --auto wrote the PNG as well as the DOT without --png being passed; the image needs Graphviz's dot on PATH. --nodes takes ids and ranges (16-21, 16,18,20-21); --roots 16 takes everything reachable from a node instead. Shapes and colours by type: goals are houses, options parallelograms, decisions diamonds, actions boxes, outcomes ellipses; chosen edges are bold green, rejected dashed red, took_from violet.

Step 2: The Writeup

$ deciduous writeup -t "Add CI pipelines" --nodes 16-21 --auto
## Summary

**Goal:** Add CI pipelines for snowflex

## Key Decisions

### Use separate workflow files: clearer separation, easier for contributors

**Options considered:**

- [ ] One workflow with test tagging and conditional jobs

## Implementation

- Implement unit test CI workflow

## Outcomes

- Unit test CI workflow runs on pull requests (90% confidence)

## Decision Graph Reference

This PR corresponds to deciduous nodes: 16, 17, 18, 19, 20, 21

--auto here finds docs/decision-graph-<branch>.png and embeds it; --png <file> names one explicitly. The image link is relative, so it resolves once the file is pushed on the branch. --no-dot drops the DOT section and --no-test-plan the checklist. "Options considered" lists the rejected options under the decision; the chosen one is the decision's own heading.

Step 3: Commit, Push, Open

Commit by name, never with -A
git add docs/decision-graph-ci-pipelines.dot docs/decision-graph-ci-pipelines.png git commit -m "docs: decision graph for the CI pipelines" git push origin ci-pipelines gh pr create --title "Add CI pipelines for snowflex" \ --body "$(deciduous writeup -t 'Add CI pipelines' --nodes 16-21 --auto)"

If the graph changes during review, regenerate both and gh pr edit <n> --body "$(deciduous writeup ...)". The workflow init wrote at .github/workflows/cleanup-decision-graphs.yml removes the .dot and .png once the PR merges, so they do not accumulate on main.

Step 4: What the Teammate Does

With a graph server (the default since 1.0.11): nothing. The repository is one workspace on the server; the nodes Alice wrote are already what Bob's deciduous nodes, his /recover and his Claude's query_nodes return. If Bob's local cache looks stale, deciduous remote pull refreshes it. The node ids differ per machine; the change ids (the CHANGE column) do not, and that is what to quote in a review comment.

Without a server: the graph travels in .deciduous/graph.json. Alice runs deciduous sync before pushing so the file holds her nodes and commits it with the code; Bob runs deciduous sync after pulling to fold them into his database. Concurrent edits to the file merge record by record through the merge driver init registered; if a clone without the driver leaves conflict markers, deciduous sync repairs the file. sync --check exits 1 when anything is pending, so it works as a pre-push check.

deciduous diff is gone

Earlier editions of this page exported a patch with deciduous diff export and had teammates run deciduous diff apply. 1.1.0 has no diff command; .deciduous/patches/ is not a thing it writes. The two mechanisms above replaced it.

When Several Agents Share One Branch Set

Parallel sessions on one repository coordinate on the message board rather than in a scratch file, because a file has no ids to answer and no way to ask what is waiting for you:

$ deciduous board post --as alice -s "CI: workflow file names" -m "Unit workflow is .github/workflows/ci.yml; integration will be integration.yml. @bob does the Snowflake account secret exist yet?"
Posted #1, to bob
$ deciduous board read --unanswered bob
#1  alice -> bob  [ci-pipelines]  2026-10-24T16:50:40.850374Z
    CI: workflow file names
    | Unit workflow is .github/workflows/ci.yml; integration will be integration.yml. @bob does the Snowflake account secret exist yet?
$ deciduous board post --as bob --reply-to 1 -s "re: CI" -m "Yes, SNOWFLAKE_TEST_DSN is in the repo secrets."
Posted #2 (reply to #1), addressed to nobody (no @label in subject or body)
$ deciduous board read --unanswered bob
Nothing addressed to bob is waiting for an answer.

A reply takes the question off the asker's list; a new post does not. The board lives in the main worktree's database, or on the server when there is one, and is never in graph.json or any export. With DECIDUOUS_AGENT_LABEL set, --as defaults to it and the board-mentions.sh hook shows that label its unanswered messages at session start. A borrow across branches is an edge, not a sentence: deciduous link <theirs> <yours> -t took_from -r "...".
