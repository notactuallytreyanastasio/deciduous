Multi-User Sync

Each developer has their own local database. Deciduous uses a dual-ID model inspired by jj to share decisions across machines without merging SQLite files.

The Dual-ID Model

The decision graph database (.deciduous/deciduous.db) is gitignored. SQLite databases do not merge well in git—concurrent writes from different branches produce conflicts that cannot be resolved automatically. Instead, deciduous gives each node two identifiers:

ID Type Scope Purpose
id (integer) Local to each machine SQLite primary key. Alice's node #57 and Bob's node #57 are different nodes.
change_id (UUID) Global across all machines Universally unique. The same node has the same change_id on every machine.

When you share nodes between machines, the change_id is what identifies them. The local id is different on each machine, but the UUID is stable. This is the same model used by jj for change IDs vs. commit IDs.

Migrating Existing Databases

If your database was created before the dual-ID feature, run deciduous migrate to add change_id columns:

deciduous migrate
deciduous migrate Migration complete: added change_id to 56 nodes, 66 edges

This is a one-time operation. New databases created with deciduous init already have change_id columns.

Exporting Patches

A patch is a JSON file containing a set of nodes and edges from your local database, identified by their change_id UUIDs. Export a patch with deciduous diff export:

Exporting a patch
deciduous diff export --nodes 57-61 -o .deciduous/patches/ci-feature.json Success: Exported 5 nodes and 4 edges to .deciduous/patches/ci-feature.json

You can also filter by branch or specify an author name:

Exporting by branch
deciduous diff export --branch ci-pipelines -o .deciduous/patches/ci-feature.json --author alice Success: Exported 5 nodes and 4 edges to .deciduous/patches/ci-feature.json

The resulting JSON file contains everything needed to recreate the nodes on another machine:

Patch file structure
{ "version": "1.0", "author": "alice", "branch": "ci-pipelines", "nodes": [ { "change_id": "a1b2c3d4-...", "node_type": "goal", "title": "Add CI pipelines for snowflex", ... }, { "change_id": "e5f6g7h8-...", "node_type": "option", "title": "Use separate workflow files", ... } ], "edges": [ { "from_change_id": "a1b2c3d4-...", "to_change_id": "e5f6g7h8-...", "rationale": "possible approach" } ] }

Applying Patches

When a teammate shares a patch file, apply it with deciduous diff apply:

Applying patches
deciduous diff apply .deciduous/patches/ci-feature.json Applied: 5 nodes (3 new, 2 updated), 4 edges (4 new)

Applying is idempotent—if you apply the same patch twice, nothing changes the second time. Nodes are matched by change_id, so there is no risk of duplicates.

Apply multiple patches at once with glob patterns:

Applying all patches
deciduous diff apply .deciduous/patches/*.json Applied ci-feature.json: 5 nodes, 4 edges Applied auth-refactor.json: 8 nodes, 7 edges Applied transport-layer.json: 12 nodes, 11 edges Total: 25 nodes (25 new, 0 updated), 22 edges

To preview what would change without actually modifying the database, use --dry-run:

Dry run
deciduous diff apply --dry-run .deciduous/patches/ci-feature.json Dry run: would apply 5 nodes (3 new, 2 updated), 4 edges (4 new)

Checking Patch Status

deciduous diff status
deciduous diff status Patches in .deciduous/patches/: ci-feature.json alice 5 nodes, 4 edges applied auth-refactor.json bob 8 nodes, 7 edges pending transport-layer.json alice 12 nodes, 11 edges applied

Event-Based Sync

For continuous synchronization beyond one-off patches, deciduous supports an event-based sync model. Every add, link, and status command automatically emits an event to .deciduous/sync/. These event files are committed to git, so they merge cleanly.

Event sync status
deciduous events status Sync: Event-based sync status Author: Robert Grayson Sync dir: .deciduous/sync Checkpoint: none Pending events: 0

After a git pull that brings in teammate events, rebuild your local database:

Rebuilding from events
deciduous events rebuild Rebuilt database from 47 events (12 new since last rebuild)

Over time, the events directory accumulates files. Compact them with a checkpoint:

Checkpointing events
deciduous events checkpoint --clear-events Checkpoint created: .deciduous/sync/checkpoint-2024-01-15.json Cleared 47 event files
The /sync skill

Your AI assistant knows the /sync skill, which automates the full event-based sync workflow: pull teammate events, rebuild the local database, and push your own events. Just type /sync in your Claude Code session.

Patches vs. Events

Approach Best For Committed to Git?
Patches (diff export/apply) PR-based sharing, one-off transfers Patch files in .deciduous/patches/
Events (events rebuild) Continuous team sync, trunk-based development Event files in .deciduous/sync/

Both approaches use the change_id UUID for node identity. You can use both simultaneously—patches for PR reviews, events for continuous sync within a shared branch.
