DECIDUOUS

One graph per repository of what was decided and why: the goal, the options weighed, the decision, the actions, the outcomes. The CLI writes it, the agent writes it over MCP while it works, and since 1.1.0 deciduous transcript import derives it from the Claude Code transcript after the fact, with every node saying what it is backed by.

That is the whole vocabulary. Seven node types (goal, option, decision, action, outcome, observation, revisit) and seven edge types (leads_to, requires, chosen, rejected, blocks, enables, took_from). The canonical flow is goal → options → decision → actions → outcomes; observations attach anywhere; a revisit is a pivot. Every node has a local id and a change_id that is the same on every machine, so two clones of a repository agree about which node is which. The graph behind this site has 1,465 nodes and 1,313 edges in the exported copy (docs/graph-data.json, exported 2026-09-04); it is browsable, and it is the history of this tool.

New in 1.1.0

The Transcript Is the Log

An agent that logs its own decisions is an agent that can forget to. The transcript cannot. Claude Code writes every session to a JSONL file under ~/.claude/projects/; deciduous transcript import reads it and derives the graph: each prompt a goal with the prompt verbatim, each run of edits or a commit an action naming the files, each build or test run an outcome with its exit and summary, the closing report an outcome too.

a three-week session that had logged nine nodes through MCP
$ deciduous transcript list
/Users/bg/.claude/projects/-Users-bg-code-deciduous
new      b30c9d4b    1 prompts  2026-10-24  Deciduous file-first memory feedback
imported cd5135a8    1 prompts  2026-10-17  Postgres port 5432 docs
new      328f8485   68 prompts  2026-09-21  Remote postgres code upstream
$ deciduous transcript import 328f8485
Imported Remote postgres code upstream (328f8485, 68 prompts)
  goals 68 · actions 119 · outcomes 67 proven, 41 inferred · observations 7 · edges 301
  50 files hashed · 52 deciduous MCP writes skipped (already in the graph)
  root goal #13: deciduous show 13

Every derived node says what it is backed by. metadata.evidence.kind is proven (a tool call and its result, or your own words, with the transcript uuids) or inferred (the assistant said so). The two sit side by side on purpose:

deciduous show, on two imported outcomes
$ deciduous show 42
Node #42 outcome
Title: cargo test passed
Description: 212 passed, 0 failed
  Evidence: proven transcript, session 328f8485, 1 tool call(s), exit ok
$ deciduous show 67
Node #67 outcome
Title: Both built, tested against the live server, and shipped.
  Evidence: inferred transcript, session 328f8485

Actions also list the files the agent Read since the previous action (metadata.consulted) and carry git blob hashes of the files they touched (metadata.file_hashes, the id git log --find-object takes). Change ids are derived from the session and entry uuids, so importing twice adds nothing and two machines importing the same transcript produce the same nodes for sync to merge. --dry-run prints the counts and writes nothing.

Not derived: decisions and options. Whether the assistant chose one approach over another is a judgement about prose, and that pass belongs to an agent reading the imported graph. Subagent transcripts are counted and skipped. Only Claude Code's format is read. The web viewer does not yet show evidence kind or file hashes; show does. docs/transcripts.md has the derivation table and a SessionEnd hook that imports at the end of every session.

Since 1.0.11

Where the Graph Lives: init Asks

Agents write through an HTTP MCP server, so a project with no server is a project whose agents have nowhere to write. deciduous init writes the slash commands, skills and a CLAUDE.md section, and then, if .deciduous/config.toml has no [remote], asks where the graph should live:

deciduous init — the server step
$ deciduous init
   This project has no server yet ([remote] in .deciduous/config.toml).
 
Where should this project's graph live?
 
  1) This machine: the deciduous server as a background service, using PostgreSQL on
     localhost:5432 as you (answering now)
  2) This machine: the server as a background service, using a PostgreSQL you name
     (any host, port, user, password)
  3) This machine, in Docker: a new PostgreSQL and the server in containers
  4) A server someone else runs: you need its URL and token
 
Choose 1-4 [1]:

Choice 1 is the default: the release's server executable (one file with Erlang and Elixir inside, checked against the release's checksums) installed under ~/.config/deciduous/server/ as a user service, a launchd LaunchAgent on macOS or a systemd user unit on Linux, listening on 127.0.0.1 only, against the PostgreSQL already on localhost:5432. It creates its database and migrates before it listens. Every later project on the machine finds it in about a second. If nothing answers on 5432 the menu says so and names the package to install. Then it stores the token in ~/.config/deciduous/credentials (mode 0600), writes [remote], and registers the server with Claude Code at user scope. In a script there is no terminal, so deciduous remote setup --local, --database-url, --docker-postgres or --url gives the answer; DECIDUOUS_NO_SERVER=1 skips the step for tests.

What the local files are for now. .deciduous/deciduous.db is a SQLite cache of the server: the CLI writes there first, appends the write as an op to .deciduous/remote-log.jsonl, and sends it to the server before the command exits (or on the next write, or deciduous remote push, if the server was down). A node an agent wrote through MCP reaches the cache on deciduous remote pull. .deciduous/graph.json, the git-tracked file that carried the graph between clones from 0.18 on, still exists for a project without a [remote]: deciduous sync reconciles it with the local database in both directions, and the deciduous merge-record git merge driver merges concurrent edits record by record. With a [remote] the graph lives on the server and update leaves graph.json, .gitignore and .gitattributes alone.

The shared graph server
MCP

Two MCP Servers

deciduous mcp runs in the binary, over stdio, against this project's local database: 34 tools, from add_node and link_nodes through trace_chain, get_pulse, export_dot, generate_writeup, the session tools, sync, and the message board. Register it with claude mcp add deciduous -- deciduous mcp, or in Claude Desktop's config with the binary's absolute path and DECIDUOUS_DB_PATH.

The shared server (deciduous_mcp/, Elixir and PostgreSQL) is the one deciduous init registers with Claude Code: 21 tools over HTTP, every call scoped by workspace, every write carrying branch. It has what several agents need and the local one does not: capture_conversation_turn (one step in one call), ask_graph, check_activity, consolidation_report, list_workspaces, took_from on log_observation. On initialize it sends the logging instructions to every client, so there is no hook to install.

what init registers (and the line to run by hand)
$ claude mcp add --scope user --transport http deciduous http://127.0.0.1:<port>/mcp --header "Authorization: Bearer $DECIDUOUS_MCP_TOKEN"
   Registered Claude Code: deciduous MCP at http://127.0.0.1:<port>/mcp (user scope; restart Claude Code)

Since 1.0

Ten Agents, One Graph

At 04:47 UTC on 22 September 2026, agent-7 implemented step reset for lock delay. The idea was agent-8's, and agent-8 had not written the code yet: it had logged a decision, agent-7 read it in the shared graph, wrote its own version, and recorded where it came from. Ten Claude Code sessions, ten git worktrees of one repository, one workspace. Twenty-six minutes later: ten playable Tetris games, 386 graph nodes, 170 borrowed ideas with provenance. The write-up has the numbers and what broke.

deciduous remote watch — the arena, live
$ deciduous remote watch
Watching: tetris-arena
04:45:14  agent-9   observation  "Took 4 hidden rows from agent-3: SRS kicks can lift a piece 2 rows at the ceiling"
04:46:13  agent-10  observation  "Took 4 hidden rows (agent-9, from agent-3) and lock-out (agent-2, from agent-1); dropped my y<0 exemption"
04:47:15  agent-7   observation  "Took the step-reset for lock delay from agent-8's decision, and spawn-then-step-down and lock-out from agent-8 and agent-3"

Nothing is refused. Every write records who wrote which branch; check_activity lists who wrote in the last five minutes and the last node on each of the twenty most recently written branches. Postgres triggers push every write over a WebSocket the moment it lands; deciduous remote watch quotes one line per write, and Claude Code's Monitor tool can sit on the same URL. A took_from edge records a borrow across branches; log_observation writes the observation and the edge in one call. In the arena zero of 471 edges crossed a branch, and the borrow counts came from a regular expression over observation titles. That is the wrong place for them.

The message board is where agents working at the same time talk: post_message / read_messages, or deciduous board. @label addresses a message, reply_to answers one, and --unanswered <label> is what is waiting for you. Messages are coordination, not graph: never in graph.json, never exported, never synced.

deciduous board
$ deciduous board post --as lead -s "header name for the limit?" -m "@w1 X-RateLimit-Remaining or Retry-After only?"
Posted #1, to w1
$ deciduous board post --as w1 -s "re header" -m "Both. @lead" --reply-to 1
Posted #2 (reply to #1), to lead
$ deciduous board read --unanswered lead
#2  w1 -> lead  re #1  [main]  2026-10-24T16:50:26.234660Z
    re header
    | Both. @lead
$ deciduous board read --unanswered w1
Nothing addressed to w1 is waiting for an answer.

/recover and /work — Memory That Outlives the Session

New session, or context compacted? /recover reads the graph, the attached documents, the recent command log, the board messages addressed to you, and the transcripts not yet imported, before it reads any code. /work creates the goal node with your verbatim request before implementation starts, so the first thing in the graph is what you asked for, in your words. deciduous pulse is the summary either one reads:

Skills

Archaeology, Narratives, Pulse — A Graph for a Project That Predates the Tool

/decision-graph reads a repository's commit history, groups commits into narratives, and writes backdated nodes (--date, --commit) grounded in real commits. The narratives skill keeps .deciduous/narratives.md, one evolution story per subsystem with its pivots. The archaeology skill turns those into graph structure, and deciduous archaeology pivot does the common case in one command, as the first screen showed: an observation, a revisit and a new decision, three edges, and the old node marked superseded. The pulse skill maps the current design as decisions: read the code, ask what decisions define it, write goal → options → decision.

deciduous narratives pivots
$ deciduous narratives pivots
=== PIVOTS === (1 found)
 
Pivot #1: [revisit #8] "Reconsidering: Token bucket in Redis, over the fixed window"
  Old approach: #4 [decision] "Token bucket in Redis, over the fixed window" (superseded)
  Triggered by: #7 [observation] "Redis cluster failover drops bucket state; limits reset on every failover"
  New approach: #9 [decision] "Fixed window counter in Postgres, 60s windows"

The graph behind this site was built this way for ripgrep's ten-year history before it was kept for deciduous itself; deciduous archaeology timeline and deciduous nodes -t revisit are how you read it back.

Evidence and output

Documents, the Viewer, DOT and PR Writeups

deciduous doc attach <node> <file> attaches a spec, a screenshot, a diagram or a PDF to a node; files are stored under .deciduous/documents/ named by content hash, so one file attached twice is stored once. --ai-describe asks the claude CLI for a description; doc detach is a soft delete and doc gc removes files no live record names.

deciduous doc
$ deciduous doc attach 1 rate-limit-spec.md -d "Rate limit spec"
Attached document 1 to node 1 (rate-limit-spec.md)
  Description: Rate limit spec
$ deciduous doc list 1
1 documents:
ID    NODE     FILENAME                  TYPE       SIZE     DESCRIPTION
1     1        rate-limit-spec.md        text/m...  34B      Rate limit spec

deciduous serve is the web viewer on port 3000: DAG, Chains, Timeline, Graph, Roadmap and Story views, and a question box (POST /api/ask) that hands your question and the graph to the claude CLI. deciduous dot --png draws the graph with Graphviz (--auto names the file after the branch, and the cleanup workflow init writes removes those images after a PR merges). deciduous writeup -t "Title" --nodes 1-9 turns a range of nodes into a PR description: the goal, the options and why they lost, the actions, the outcomes. The live graph on this site is the static export of this repository's graph as of 2026-09-04; since 1.0.5 deciduous sync no longer writes docs/graph-data.json, because the graph lives on the server and is browsed with serve.

Install

Homebrew (macOS or Linux)
$ brew tap notactuallytreyanastasio/tap
$ brew install deciduous
Cargo (needs a Rust toolchain)
$ cargo install deciduous --locked

Or a pre-built binary: deciduous-linux-amd64, deciduous-linux-arm64, deciduous-darwin-amd64, deciduous-darwin-arm64, deciduous-windows-amd64.exe. The current release is 1.1.0; deciduous --version says which one is on your PATH, and which -a deciduous says whether there is a second.

If the graph will live on this machine (the default), you need a PostgreSQL on localhost:5432: the one you have, or brew install postgresql@17 && brew services start postgresql@17, or your distribution's package. Docker is optional; it is choice 3 in the menu. Then cd your-project && deciduous init, answer where the graph lives, commit the project files it wrote, and restart Claude Code. Upgrading later is brew upgrade deciduous or the same cargo install line, then deciduous update in each project (deciduous update --all ~/code for many); since 1.0.12 update keeps every section and command file you edited.

2

Work

The agent writes to the graph as it goes, through the MCP tools, and the CLAUDE.md section says when. Nothing blocks it if it does not: up to 1.0.2 a hook denied the agent's next tool call until it logged, and it could leave a session unable to do anything. 1.0.3 removed it. The two hooks left are a once-a-day version check and the board-mentions hook, which prints a labelled session's unanswered messages.

3

Import the transcript

At the end of a session, or from a SessionEnd hook, deciduous transcript import <session-id> adds what the agent did not log, with evidence on every node. deciduous transcript list says which sessions are new. Then /recover at the start of the next one.

Works With Your Editor

deciduous init sets up Claude Code by default. deciduous update detects which of .claude/, .opencode/ and .windsurf/ exist and updates them all.

Claude Code deciduous init
OpenCode deciduous init --opencode
Windsurf deciduous init --windsurf
Claude Code + OpenCode deciduous init --both

OpenCode and Windsurf files have no remote-aware versions yet (CHANGELOG 1.0.12); they describe the graph.json model.

Seven Node Types

goal → options → decision → actions → outcomes. Observations attach anywhere. A revisit connects an old approach to a new one. Statuses are pending, active, completed, rejected, superseded and abandoned.

Goal

What was asked for, verbatim in prompt

Option

An approach considered

Decision

The option chosen, and what it beat

Action

Code or config changed, with files and commit

Outcome

What happened: the number or the error

Observation

A fact that changes the plan

Revisit

An earlier choice turned out wrong

What init Installs

Slash commands (/recover) and skills, for Claude Code. The CLI itself is documented in the guide.

NameTypeWhat It Does
/recover command Session start. Reads the graph, attached documents, the command log, unanswered board messages, transcripts not yet imported, and git state. Reports what is active and what is next.
/work command Creates the goal node with the verbatim prompt before any code is written, then tracks actions and outcomes through to the commit.
/decision command Graph management: add nodes, link edges, attach documents, sync, export DOT and PR writeups.
/decision-graph command Build a graph from an existing repository's commit history: narratives first, then backdated nodes citing real commits.
/document command Document a file or directory: callers, tests, dependencies.
/sync command Reconcile .deciduous/graph.json with the local database after a pull and before a push (projects without a [remote]); remote pull and remote status in projects with one.
/serve-ui command Start the web viewer on localhost:3000.
/build-test command Build the project and run its tests.
/demo-swarm command A demonstration: an Opus lead and four Sonnet workers build one Tetris on one graph, in iTerm2 or Ghostty panes (macOS). deciduous demo-swarm --preview plays the walkthrough without starting anything.
pulse skill Map the current design as decisions: pick a scope, read the code, write goal → options → decision. deciduous pulse is the summary.
narratives skill Keep .deciduous/narratives.md: one evolution story per subsystem, with its pivots and evidence in commits.
archaeology skill Turn narratives into graph structure: backdated goals, archaeology pivot for pivot chains, archaeology supersede, archaeology timeline.
version-check.sh, board-mentions.sh hooks The only two hooks. One checks crates.io for a newer release once a day; the other shows a session with DECIDUOUS_AGENT_LABEL set its unanswered board messages. Neither blocks anything.
