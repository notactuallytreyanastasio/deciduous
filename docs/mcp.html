Two MCP Servers

The agent writes to the graph through MCP while it works. There are two servers it can write through, and deciduous init gives you one of them without asking. This page says which, and how Claude Code and Claude Desktop reach each.

After deciduous init on a 1.0.5 or newer binary, Claude Code has the shared server. init does not finish until the project points at a server that answers: this machine's (a background service against the PostgreSQL on localhost:5432, since 1.0.11), or one someone else runs. It then runs claude mcp get deciduous, and if nothing is registered under that name, claude mcp add at user scope with the URL and the bearer token. An existing deciduous registration is left alone. Restart Claude Code and the tools are mcp__deciduous__* in every directory.

The local server is for a project kept without a [remote] (the graph.json model), for Claude Desktop, or for the tools the shared server does not have. With a [remote] configured, writes made through it are also queued in .deciduous/remote-log.jsonl and sent to the server (CHANGELOG 1.0.8), so using both does not fork the graph.

Claude Code

the shared server: what init ran, to run by hand for another machine or client
claude mcp add --scope user --transport http deciduous http://127.0.0.1:<port>/mcp --header "Authorization: Bearer $DECIDUOUS_MCP_TOKEN"
The URL is [remote] url in .deciduous/config.toml plus /mcp: this machine's server on 127.0.0.1 and the port init asked for, or https://<host>/deciduous-mcp for one someone else runs. The token is in ~/.config/deciduous/credentials; DECIDUOUS_MCP_TOKEN in the environment overrides it.
the local server, for this project
claude mcp add deciduous -- deciduous mcp
Project scope by default; add --scope user to have it in every project, where it opens whichever .deciduous/ it finds walking up from the current directory (or DECIDUOUS_DB_PATH). Give it another name if the shared server is already registered as deciduous.

Claude Code reads MCP servers from claude mcp add or a project .mcp.json, not from .claude/settings.local.json; a README that said otherwise connected nothing until 1.0.5 fixed it. A repository that wants its workspace fixed whatever a tool call says pins it in .mcp.json with the X-Deciduous-Workspace header, and the token as ${DECIDUOUS_MCP_TOKEN}, never a literal; see pinning a repository.

Claude Desktop

~/Library/Application Support/Claude/claude_desktop_config.json (macOS); %APPDATA%\Claude\claude_desktop_config.json (Windows)

{
  "mcpServers": {
    "deciduous": {
      "command": "/Users/you/.cargo/bin/deciduous",
      "args": ["mcp"],
      "env": {
        "DECIDUOUS_DB_PATH": "/path/to/your/project/.deciduous/deciduous.db"
      }
    }
  }
}

Use the absolute path to the binary (which deciduous); Claude Desktop does not inherit your shell PATH. DECIDUOUS_DB_PATH names the project, since Desktop has no working directory to walk up from. Restart Claude Desktop. This is the local server; whether Claude Desktop can carry the bearer header the shared server needs has not been verified for this page, so no configuration for it is given here.

What the agent is told, and how it writes

The shared server's initialize result carries an instructions string that the client puts in the model's context for the whole session. It says when to write (a request, a fork, a choice, a change, a result, a fact that changes the plan), names capture_conversation_turn as the one-call step and add_node with parent_id for a single node, and asks for workspace and branch on every write. It reaches every client with no project configuration, and it cannot block anything. That replaced the hook 1.0.3 removed.

one step, one call (shared server)
Claude
capture_conversation_turn({ workspace: "my-api", branch: "rate-limit", summary: "Chose a Redis token bucket for rate limiting and implemented the middleware.", goal: { title: "Add rate limiting to the public API", prompt: "Add rate limiting to the public API. Per-token, 100 req/min, 429 with Retry-After." }, options_considered: [ { title: "Token bucket in Redis", chosen: true }, { title: "Fixed window counter in Postgres" } ], decision: { title: "Token bucket in Redis, over the fixed window", rationale: "smooths bursts; Redis already deployed; window edges allow 2x burst" }, action: { title: "Implement RateLimiter middleware", files: ["src/middleware/rate_limit.rs"] }, outcome: { title: "cargo test: 41 passed, 0 failed", success: true } })
Why one call
The two-step form made agents write add_edge beside add_node with "PLACEHOLDER" where the new id belonged, five times in one night (CHANGELOG 1.0.2). The server refuses such an id now and points at parent_id. capture_conversation_turn writes the step's nodes and edges in one transaction, all or nothing; pass parent_node_id to put it under the goal you are working on.

A single node goes through add_node with parent_id (and edge_type, rationale); a borrow from another branch through log_observation with took_from and why; a choice through log_decision; the end of a line of work through close_thread. To make a retried add_node safe, give it a change_id: the same one again returns the node already made. The local server has none of these composites: it is add_node then link_nodes, and the arguments are listed in the API reference.

Reading the graph

On the shared server, ask_graph takes a question in prose and says how each answer was reached, and when the graph has nothing on the subject:

ToolWhat it answers
ask_graph"Why did we pick X?" Entry nodes by trigram and full-text match, then the edges the question calls for (choices and revisits for why, superseded nodes for history, requires/blocks for depends). Each result carries reached_by and path. A question naming something the graph never recorded gets stop_reason: "distinctive_term_unmatched" and at most three nodes, instead of 25 unrelated ones. workspace: "*" asks every project.
query_nodesFilter by type, status, branch, text, and file: what was decided about a path, with the decisions up to three edges above it.
show_nodeOne node, its edges, documents, themes, and related: nodes that name the same file or commit, found at read time, never stored as edges.
check_activityWho wrote to this workspace in the last five minutes and the last node on each branch. Writes are never refused; this is how you see the others.
consolidation_reportLikely duplicate goals, competing decisions with no revisit between them, stale pending actions, parentless nodes with a suggested parent. Changes nothing.
list_workspacesEvery project on the server, with counts: the index for the workspace argument.

Sessions, on the local server only

start_session creates a root goal and a session id; later nodes are associated with it; get_session, resume_session and list_sessions read it back; end_session closes it. The current id is kept in .deciduous/active_session, so it survives a restart of the server process. The shared server has no sessions: a conversation there is scoped by workspace and branch, and check_activity is how one session sees another.

The message board, on both

post_message and read_messages have the same arguments on both servers. Agents working at the same time put interface changes, questions and answers there, never in a scratch file: @label addresses a message, reply_to answers one, and read_messages with unanswered_for your own label, at start and before finishing, is what is waiting for you. Messages are not graph nodes and are not exported. Locally the board is the main worktree's database, shared by every worktree; with a [remote] it is on the server, which must be 1.0.9 or newer.
