MCP API Reference

Two servers, 55 tools, as deciduous 1.1.0 declares them. Shared server (21 tools, HTTP) first; local stdio server (34 tools) below.
← Which server you have, and how each client reaches it

Tool names and arguments on this page are read from the source that declares them: deciduous_mcp/lib/deciduous_mcp/mcp/tools/*.ex for the shared server and src/mcp/tools.rs for the local one. Both servers refuse an argument they do not declare and name the one they meant. Required arguments are marked. Where the two servers have a tool of the same name (add_node, delete_node, show_node, get_graph, find_orphans, post_message, read_messages), the arguments differ: the shared server names nodes by UUID and takes workspace; the local one takes a local integer id or a change_id prefix.

Shared server (21 tools, HTTP)

This is the server deciduous init registers with Claude Code. Every tool takes workspace: the project's name, workspace under [remote] in .deciduous/config.toml. Reads marked cross-project accept workspace: "*" for every project at once; writes refuse it. A repository pinned with the X-Deciduous-Workspace header cannot be written anywhere else. Every write takes branch: it is not a lock, it is the record check_activity reads.

add_edgedeciduous link

Params: from_node_id, to_node_id (UUIDs, req), edge_type (leads_to default, chosen, rejected, requires, blocks, enables, took_from: from = the node you took from, to = your node that used it), rationale, branch, workspace.

Reading

ask_graphcross-project

A question in prose. Finds entry nodes by text (trigram and full-text, fused by reciprocal rank), then follows the edges the question calls for: why/decided questions follow choices and revisits, history questions follow revisits and superseded nodes, blocked/depends questions follow requires/blocks. Each result says how it was reached (reached_by, path). unmatched_terms lists question words nothing in the graph contains; when one is a name or not a common English word, stop_reason is distinctive_term_unmatched and at most 3 nearest matches come back, so a question about something never recorded is answered as such.

ParamTypeRequiredDescription
questionstringYes
scopestringall, active (non-completed), decisions, goals, observations, recent (last 50 nodes)
include_contextboolInclude ancestors/descendants of each result (default true)
workspacestringThe project, or "*"
query_nodesdeciduous nodescross-project

Search and filter nodes.

ParamTypeDescription
typestringgoal, decision, option, action, outcome, observation, revisit, feedback
statusstringpending, active, completed, rejected, superseded, abandoned, done
branchstring
searchstringText in title and description
filestringOnly nodes whose metadata.files names this path (trimmed, leading ./ dropped, // collapsed; a path ending in / matches everything under it). Each node carries file_match: exact, under_dir or dir_contains; decisions_above lists up to 20 decisions within 3 edges above a node naming the file; file_node_count counts every node naming it. Needs one workspace, not *
limitint 1-10000Default 100
workspacestringThe project, or "*"
check_activity

Who has been writing to this workspace in the last five minutes: each session's branch, client (MCP or the deciduous CLI) and whether it is you; and the most recent node on every branch. Writes are never refused because someone else is writing; this is how you see them. Call it before a burst of writes and after every milestone instead of polling query_nodes.

ParamTypeDescription
branchesint 0-200How many branches to list under branches, most recently written first (default 20). branches_total says how many the workspace has
workspacestringThe project
consolidation_report

Read-only. Four lists, each finding with node ids and the update_node / add_edge that would act on it: duplicate_goals (trigram-similar goal titles, labelled merge, keep_separate or uncertain with the evidence), competing_decisions (similar live decisions under the same option or goal with no revisit between them), stale_actions (pending actions older than stale_days with no outcome), and parentless actions and outcomes (the first 10, each with a ranked suggested_parent, never linked). Bounded; every cap and what it cut is in the result.

ParamTypeDescription
similaritynumberpg_trgm title similarity a pair needs to be examined
stale_daysintAn action with no outcome is stale after this many days
max_pairsintMost similar pairs examined per section
max_itemsintMost stale or parentless nodes listed
max_nodesintMost goals, and most decisions, compared pairwise, newest first
workspacestringThe project

Defaults and bounds are the server's (Consolidation.defaults/0); the tool's schema states them.

show_nodedeciduous show

One node with its edges, documents and themes. related lists up to 10 nodes of the same workspace that name one of this node's files or its commit, best overlap first, read off metadata, not edges. Params: node_id (UUID, req), workspace.

get_graphdeciduous graphcross-project

Nodes, edges, themes and documents of one workspace: titles, types, status and branch by default. Params: branch, include_details (descriptions, metadata, edge rationales; about 3x the bytes), max_nodes (refuses a larger graph; use query_nodes or GET /export), workspace.

get_ancestors

Walk backward from a node. Params: node_id (UUID, req), max_depth (1-200, default 50), max_nodes (1-5000, default 1000), workspace.

get_descendants

Walk forward from a node. Same params as get_ancestors.

find_orphanscross-project

Nodes with no incoming edges that are not goals. Params: suggest_parents (bool: rank likely parents for the first orphans, never linked for you), workspace.

list_workspaces

Every project on the server with node and edge counts, most populated first. No params. This is how to learn what workspace should be.

Message board

post_messagedeciduous board post

Params: author (your label, req), subject (one line, req), body (at most 64 KiB, req), reply_to (id of the message this answers, in this workspace), branch, workspace. @label in subject or body addresses it. Messages are not graph nodes and are not exported.

read_messagesdeciduous board read

Oldest first. Params: unanswered_for (messages that mention this label and that it has not replied to), since_id (the latest_id of a previous read), author, to, query (full-text, web search syntax: "a phrase", or, -word), id, limit, branch, workspace. Returns messages, latest_id, truncated.

Not tools, on the same host: GET /events?workspace=<name> (or *) is a WebSocket with one JSON frame per node insert or update, edge insert and board post; deciduous remote watch is its client. POST /ops is where the CLI replays .deciduous/remote-log.jsonl; GET /export is the whole workspace as a file; GET /health and GET /ready are liveness and readiness. The shared graph page covers them.

Local stdio server (34 tools): deciduous mcp

One project, this repository's .deciduous/deciduous.db, over stdin/stdout. Node ids are the local integer id or a change_id prefix (["integer", "string"] in the schema). There is no workspace argument except on the two board tools, where it is optional and must be this project's. With a [remote] configured, every write made here is also queued in .deciduous/remote-log.jsonl and sent to the server (CHANGELOG 1.0.8). This server does not send instructions on initialize; the CLAUDE.md section init writes is what tells the agent when to log.

Sessions (local server only)

A session is a root goal that later nodes are associated with. The current session id is kept in .deciduous/active_session, next to the database, so it survives a server restart. The shared server has no sessions; there a conversation is scoped by workspace and branch.

start_session

Params: name, goal_title (req), goal_prompt (verbatim). Creates the root goal and returns the session id.

end_session

Param: summary.

get_session

Param: session_id (omit for the current one). Returns the session and its nodes.

resume_session

Param: session_id (req). Reopens what it says it resumed.

list_sessions

Param: active_only (bool).

Sync (projects without a [remote])

sync_statusdeciduous sync --check

Whether .deciduous/graph.json exists, how many records it holds, and how many changes are pending in each direction. No params.

syncdeciduous sync

Reconcile the local database with .deciduous/graph.json in both directions; creates the file on first use. Param: dry_run (bool).

Message board

Same arguments as on the shared server, and additionalProperties: false: an unknown argument is refused. Locally the board is the main worktree's database, so every git worktree of a repository reads one board; with a [remote] the tools post to the server, which must be 1.0.9 or newer (an older one is an error, never a quiet fall back to the local table).

post_messagedeciduous board post

Params: author (1-100 chars), subject (1-300), body (1-65536) (req); reply_to (must exist on this board), branch (default: current), workspace (optional; another project's is refused).

read_messagesdeciduous board read

Params: unanswered_for, since_id, author, to, query (case-insensitive substring here; stemmed full-text on the server), id, limit (1-200, default 50), branch, workspace. Returns messages, latest_id, truncated.

Where the local server lives in the source

Functional core, imperative shell: the tool definitions and the dispatch table are pure data and functions; only mod.rs touches stdin and stdout.
