Deciduous Guide

The CLI, walked through on 1.1.0. Every command on this page was run against the release binary; every flag is in its --help.

What the Graph Is

A new session of Claude Code knows nothing about the last one. Compaction keeps a summary; the summary does not keep the option you rejected or the reason you rejected it. Deciduous keeps a graph per repository of exactly that:

[goal] "Add rate limiting to the public API" prompt: the user's words, verbatim | +--> [option] "Token bucket in Redis" +--> [option] "Fixed window counter in Postgres" | | chosen rejected: "window edges allow 2x burst" v v [decision] "Token bucket in Redis, over the fixed window" | +--> [action] "Implement RateLimiter middleware" files: src/middleware/rate_limit.rs | +--> [outcome] "cargo test: 41 passed, 0 failed" | +--> [observation] "Redis cluster failover drops bucket state" +--> [revisit] "Reconsidering: Token bucket in Redis" +--> [decision] "Fixed window counter in Postgres, 60s windows"

Seven node types: goal, option, decision, action, outcome, observation and revisit. Seven edge types: leads_to, requires, chosen, rejected, blocks, enables, took_from. The flow is goal → options → decision → actions → outcomes. Goals do not lead straight to decisions: the options come first, because the rejected one is the part you will want back.

Three things write the graph. The CLI below. The MCP tools the agent calls while it works (two servers). And since 1.1.0, deciduous transcript import, which derives the graph from the Claude Code transcript after the fact, so a session that logged nothing is still in it.

Quick Start

1 Install 
brew tap notactuallytreyanastasio/tap && brew install deciduous   # macOS or Linux
cargo install deciduous --locked                                    # or, with a Rust toolchain
deciduous --version                                                  # deciduous 1.1.0

Or a binary from the releases page: deciduous-linux-amd64, deciduous-linux-arm64, deciduous-darwin-amd64, deciduous-darwin-arm64, deciduous-windows-amd64.exe.

2 Initialize, and answer where the graph lives 
cd your-project
deciduous init            # Claude Code; --opencode, --windsurf, --both for others

init writes .deciduous/, nine slash commands and three skills under .claude/, two hooks that never block, and a CLAUDE.md section. Then, if .deciduous/config.toml has no [remote], it asks where the graph should live: this machine (the server as a background service against your PostgreSQL on localhost:5432, the default), a PostgreSQL you name, Docker, or a server someone else runs. It stores the token outside the repository, writes [remote], and registers the server with Claude Code. Restart Claude Code. In a script: deciduous remote setup --local (or --database-url, --docker-postgres, --url); DECIDUOUS_NO_SERVER=1 skips the step for tests. The shared graph page shows the menu and what each choice does.

3 Write as you go 
deciduous add goal "Add dark mode toggle" -c 90 -p "Add a dark mode toggle to settings"
deciduous add option "CSS variables switched by a class on body" -c 80
deciduous add option "Second stylesheet loaded on toggle" -c 50
deciduous link 1 2 -r "possible approach"
deciduous link 1 3 -r "possible approach"
deciduous add decision "CSS variables, over a second stylesheet" -c 85
deciduous link 2 4 -t chosen -r "one file, no flash on load"
deciduous link 3 4 -t rejected -r "two stylesheets drift"
deciduous add action "Add ThemeContext and the toggle" -c 85 -f "src/theme.tsx,src/settings.tsx"
deciduous link 4 5 -r "implementation"
git commit -m "feat: dark mode toggle"
deciduous add outcome "Toggle works; 14 tests pass" -c 95 --commit HEAD
deciduous link 5 6 -r "result"
4 Read it back 
deciduous nodes              # every node: id, change_id prefix, type, status, title
deciduous edges              # every edge with its rationale
deciduous show 4             # one node, its metadata and connections
deciduous pulse              # summary, active goals as a tree, coverage gaps
deciduous serve              # web viewer at http://localhost:3000
Import the transcript at the end. deciduous transcript list shows this project's Claude Code sessions and which are already imported; deciduous transcript import <session-id> adds what the agent did not log, each node saying whether it is proven by a tool result or inferred from what the assistant said. See docs/transcripts.md.

A Walkthrough: Rate Limiting, Then a Pivot

This is a real session against a fresh project on 1.1.0, output included. Click a phase to expand it.

Phase 1: The request, verbatim A goal with the prompt
▶
Add rate limiting to the public API. Per-token, 100 req/min, 429 with Retry-After.
The goal carries the request word for word. -p for one line, --prompt-stdin for several. 
$ deciduous add goal "Add rate limiting to the public API" -c 90 -p "Add rate limiting to the public API. Per-token, 100 req/min, 429 with Retry-After."
Warning: Prompt is only 82 chars. This looks like a summary, not a full prompt.
         Capture the verbatim user message for better context recovery.
Created node 1 (type: goal, title: Add rate limiting to the public API) [confidence: 90%] [prompt: 82 chars] [branch: main]
The warning is a heuristic. A short prompt is often a summary someone typed instead of the user's message. Here the user's message really was 82 characters; the node is created either way. A multi-line request goes in with --prompt-stdin << 'EOF'.
Phase 2: Options, then the decision chosen and rejected edges carry the reasons
▶ 
$ deciduous add option "Token bucket in Redis" -c 70
Created node 2 (type: option, title: Token bucket in Redis) [confidence: 70%] [branch: main]
$ deciduous add option "Fixed window counter in Postgres" -c 60
Created node 3 (type: option, title: Fixed window counter in Postgres) [confidence: 60%] [branch: main]
$ deciduous link 1 2 -r "possible approach"
Created edge 1 (1 -> 2 via leads_to)
$ deciduous link 1 3 -r "possible approach"
Created edge 2 (1 -> 3 via leads_to)

$ deciduous add decision "Token bucket in Redis, over the fixed window" -c 85
Created node 4 (type: decision, title: Token bucket in Redis, over the fixed window) [confidence: 85%] [branch: main]
$ deciduous link 2 4 -t chosen -r "smooths bursts; Redis already deployed"
Created edge 3 (2 -> 4 via chosen)
$ deciduous link 3 4 -t rejected -r "window edges allow 2x burst"
Created edge 4 (3 -> 4 via rejected)
Why the options point at the decision and not the other way. The decision is what the options led to; the edge type says which one won. Six months on, deciduous show 4 prints both edges with their rationale, which is the answer to "why not Postgres?".
Phase 3: Action before the code, outcome after files on the action, the number on the outcome
▶ 
$ deciduous add action "Implement RateLimiter middleware" -c 85 -f "src/middleware/rate_limit.rs"
Created node 5 (type: action, title: Implement RateLimiter middleware) [confidence: 85%] [files: src/middleware/rate_limit.rs] [branch: main]
$ deciduous link 4 5 -r "implementation"
Created edge 5 (4 -> 5 via leads_to)

# ... the code is written and tested ...

$ deciduous add outcome "cargo test: 41 passed, 0 failed" -c 95
Created node 6 (type: outcome, title: cargo test: 41 passed, 0 failed) [confidence: 95%] [branch: main]
$ deciduous link 5 6 -r "result"
Created edge 6 (5 -> 6 via leads_to)
$ deciduous status 5 completed
Updated node 5 status to 'completed'
$ deciduous status 6 completed
Updated node 6 status to 'completed'
An outcome is a number or an error, not an adjective. "Rate limiting working" cannot be checked later; "41 passed, 0 failed" can. After a commit, --commit HEAD stores the full hash on the node (a rev git cannot resolve in this checkout is refused).
Phase 4: The pivot, in one command observation, revisit, new decision; old decision superseded
▶
Redis cluster failover keeps resetting the limits. Can we not depend on it?
A pivot is seven commands by hand. archaeology pivot does them atomically, and --dry-run shows the plan first. 
$ deciduous archaeology pivot 4 "Redis cluster failover drops bucket state; limits reset on every failover" "Fixed window counter in Postgres, 60s windows" -c 80 -r "Bucket state does not survive Redis failover"
=== PIVOT CREATED ===

  #7 [observation] "Redis cluster failover drops bucket state; limits reset on every failover"
    └── linked from #4 "Token bucket in Redis, over the fixed window"
  #8 [revisit] "Reconsidering: Token bucket in Redis, over the fixed window"
    └── linked from #7 [observation]
  #9 [decision] "Fixed window counter in Postgres, 60s windows"
    └── linked from #8 [revisit]

  Superseded: #4 "Token bucket in Redis, over the fixed window" -> status: superseded

  Summary: 3 nodes created, 3 edges created, 1 node superseded
$ deciduous narratives pivots
=== PIVOTS === (1 found)

Pivot #1: [revisit #8] "Reconsidering: Token bucket in Redis, over the fixed window"
  Old approach: #4 [decision] "Token bucket in Redis, over the fixed window" (superseded)
  Triggered by: #7 [observation] "Redis cluster failover drops bucket state; limits reset on every failover"
  New approach: #9 [decision] "Fixed window counter in Postgres, 60s windows"
The superseded decision stays. deciduous nodes -t decision lists both, one marked superseded; that is the history, and deleting it would delete the reason the new approach exists.
Phase 5: Evidence and a note to a colleague a document on the goal; the message board
▶ 
$ deciduous doc attach 1 rate-limit-spec.md -d "Rate limit spec"
Attached document 1 to node 1 (rate-limit-spec.md)
  Description: Rate limit spec
$ deciduous doc list 1
1 documents:
ID    NODE     FILENAME                  TYPE       SIZE     DESCRIPTION
--------------------------------------------------------------------------------
1     1        rate-limit-spec.md        text/m...  34B      Rate limit spec

Files go to .deciduous/documents/ under a content-hash name, so the same file attached twice is stored once. doc detach is a soft delete; doc gc removes files no live record names.

$ deciduous board post --as lead -s "header name for the limit?" -m "@w1 X-RateLimit-Remaining or Retry-After only?"
Posted #1, to w1
$ deciduous board post --as w1 -s "re header" -m "Both. @lead" --reply-to 1
Posted #2 (reply to #1), to lead
$ deciduous board read --unanswered lead
#2  w1 -> lead  re #1  [main]  2026-10-24T16:50:26.234660Z
    re header
    | Both. @lead
$ deciduous board read --unanswered w1
Nothing addressed to w1 is waiting for an answer.

The board is for agents (or people) working at the same time. @label addresses, --reply-to answers, --unanswered LABEL is the inbox. It lives in the main worktree's database, shared by every worktree, or on the server when the project has a [remote]; never in graph.json, never exported.

Let's continue the rate limiting work. Where were we?

    ├── #6 [outcome] cargo test: 41 passed, 0 failed (completed) 95%

The last line is the answer. A decision was made and nothing has been done about it. deciduous show 9 gives the rationale; deciduous show 1 gives the original request and the attached spec; deciduous commands gives the recent command log. /recover runs these, plus board read --unanswered and transcript list, before touching code.

Patterns

goal A request
deciduous add goal "Title" -c 90 \
  --prompt-stdin << 'EOF'
[the user's message, word for word]
EOF

A root goal is the only node allowed to have no parent. A follow-up request links under it.

decision A choice
deciduous add option "A"
deciduous add option "B"
deciduous link GOAL A -r "possible approach"
deciduous link GOAL B -r "possible approach"
deciduous add decision "A, over B"
deciduous link A DECISION -t chosen -r "why"
deciduous link B DECISION -t rejected -r "why not"

The decision's title names what it beat.

action Before the edit
deciduous add action "What is about to change" \
  -c 85 -f "src/a.rs,src/b.rs"
deciduous link DECISION ACTION -r "implementation"

Files on the action; the shared server's query_nodes file= and show_node related find them later.

outcome After the result
deciduous add outcome "212 passed, 0 failed" \
  -c 95 --commit HEAD
deciduous link ACTION OUTCOME -r "result"
deciduous status ACTION completed

The number or the error. --commit stores the full hash.

observation A fact that changes the plan
deciduous add observation "Title" \
  -d "What was seen and what it implies"
deciduous link GOAL OBS -r "found while ..."

Observations attach anywhere. An observation that overturns a decision is the first step of a pivot.

revisit: a pivot
deciduous archaeology pivot OLD_DECISION \
  "What was learned" "New approach" \
  -c 80 -r "Why the old one failed" [--dry-run]

Observation, revisit, new decision, three edges, old node superseded. archaeology supersede ID --cascade marks a whole subtree.

The rule

BEFORE you change something  ->  action: what is about to change, and in which files
AFTER it succeeds or fails   ->  outcome: the number or the error
WHEN you choose              ->  options first, then the decision that names what it beat
ALWAYS                       ->  link the node to its parent in the same breath

What not to log: your own reading, searching and planning. The graph records the project's decisions, not the agent's process. "Analyzing the codebase" is not a node; "the existing auth uses bcrypt, reuse it" is an observation.

Command Reference

Every flag below is in deciduous <command> --help on 1.1.0. Anywhere a node is named, a local id, a change_id prefix (the CHANGE column of deciduous nodes) or a server id works.

Nodes

deciduous add <type> "Title"           # goal, option, decision, action, outcome, observation, revisit
  -d, --description "..."              # longer text (observations want one)
  -c, --confidence 0-100
  -p, --prompt "..."  |  --prompt-stdin  # the user's words, verbatim
  -f, --files "a.rs,b.rs"
      --commit HEAD|<rev>              # stored as the full hash; an unresolvable rev is refused
  -b, --branch NAME  |  --no-branch    # branch is auto-detected otherwise
      --date "YYYY-MM-DD"              # backdate, for archaeology

deciduous status <id> <status>          # pending, active, completed, rejected, superseded, abandoned
deciduous prompt <id> ["text"]          # set or replace the prompt; stdin when omitted
deciduous delete <id> [--dry-run]       # the node and every edge on it

Edges

deciduous link <from> <to> -r "rationale" [-t leads_to|requires|chosen|rejected|blocks|enables|took_from]
deciduous unlink <from> <to> [-t TYPE]  # -t is required when two edge types join the same nodes

took_from records a borrow: from the node you took the idea from, to your node that used it, usually across branches. A duplicate link is refused by name; a self-loop is refused.

Reading

deciduous nodes [-b BRANCH] [-t TYPE] [--theme NAME]   # there is no --status filter on the CLI
deciduous edges
deciduous show <id> [--json]            # metadata, connections, documents; evidence on imported nodes
deciduous graph                         # the whole graph as JSON, to stdout
deciduous pulse [-b BRANCH] [-r N] [--summary] [--json]
deciduous commands [-l N]               # recent command log
deciduous archaeology timeline [-l N] [-t TYPE] [-b BRANCH] [--json]
deciduous narratives pivots [-b BRANCH] [--json]

Pivots and archaeology

deciduous archaeology pivot <from> "observation" "new approach" [-c N] [-r "reason"] [--dry-run]
deciduous archaeology supersede <id> [--cascade] [--dry-run]
deciduous narratives init [-o PATH] [--force]   # .deciduous/narratives.md from the active goals
deciduous narratives show [-p PATH]
deciduous audit --associate-commits [--min-score 50] [--dry-run] [--yes]   # match node titles to commit messages

Transcripts

deciduous transcript list [--dir DIR] [--json]              # this project's sessions; "new" or "imported"
deciduous transcript import <path|session-id>... [--dry-run] [--no-hash] [--json]

A session id is any prefix of the file name under ~/.claude/projects/<slug>/. Importing twice adds nothing. --no-hash skips hashing the files the actions touched, for a SessionEnd hook that may run mid-edit.

Documents, themes

deciduous doc attach <node> <file> [-d "..."] [--ai-describe]
deciduous doc list [node] [--include-detached] [--json]
deciduous doc show <doc> [--json]  |  doc describe <doc> ["text"|--ai]  |  doc open <doc>
deciduous doc detach <doc>         |  doc gc [--dry-run]
deciduous themes create NAME [-c "#hex"] [-d "..."]  |  themes list  |  themes delete NAME
deciduous tag add <node> THEME  |  tag remove  |  tag list <node>  |  tag suggest [node] [--apply]  |  tag confirm <node> THEME

Output

deciduous serve [-p 3000]               # web viewer; --api runs the multi-graph JSON API daemon instead
deciduous dot [-o FILE] [-r ROOTS] [-n "1-11"] [-t "Title"] [--rankdir TB|LR|BT|RL] [--png] [--auto]
deciduous writeup [-t "Title"] [-r ROOTS] [-n "1-11"] [-o FILE] [--png FILE | --auto] [--no-dot] [--no-test-plan]
deciduous backup [-o FILE]              # copy of the SQLite database

--png needs Graphviz. --auto names the file after the branch (docs/decision-graph-<branch>.png), and the cleanup workflow init writes removes those images after the PR merges.

Where the graph lives

deciduous remote setup [--local | --database-url URL | --docker-postgres | --docker | --url URL] [--port N]
deciduous remote status                 # local cache vs server, field by field; exit 1 if anything differs
deciduous remote pull                   # refresh the local database from the server
deciduous remote push [--seed] [--repair] [--drop-rejected | --retry-rejected | --drop OP]
deciduous remote watch [--types T,T] [--branch B] [--edges] [--json] [--url [--claude-code]]
deciduous remote login [--url URL]  |  remote logout  |  remote init URL [--workspace NAME]  |  remote adopt [ROOT] --url URL [-n]

deciduous sync [--check]                # projects without a [remote]: reconcile .deciduous/graph.json with the database

With a [remote], add, link, status and the rest write locally, append an op to .deciduous/remote-log.jsonl, and send it before the command exits; push is for a backlog or for history that predates the server. Without one, sync after git pull and before git push is how teammates' nodes arrive and yours leave; sync --check exits 1 when anything is pending. sync no longer writes docs/graph-data.json (removed in 1.0.5).

Agents

deciduous board post --as LABEL -s "subject" [-m "body" | < stdin] [--reply-to ID] [--branch B] [--json]
deciduous board read [--since ID] [--from LABEL] [--to LABEL] [--unanswered LABEL] [-q TEXT] [--limit N] [--json]
deciduous board show ID [--json]
deciduous mcp                           # the local stdio MCP server, 34 tools

--as defaults to DECIDUOUS_AGENT_LABEL, which the board-mentions.sh hook also reads to show a session its unanswered messages at start.

Maintenance

deciduous check-update                  # exit 1 if .deciduous/.version is behind the binary
deciduous update [--all DIR]            # replace files deciduous wrote; keep files and sections you edited
deciduous integration                   # what is installed for Claude Code
deciduous completion zsh|bash|fish|powershell|elvish
deciduous auto-update on|off            # the once-a-day crates.io check

Troubleshooting

Nothing blocked the agent, and it did not log

That is by design since 1.0.3. Up to 1.0.2 a hook denied the agent's next tool call until it wrote to the graph, and it could leave a session unable to do anything. The two hooks init installs now (version check, board mentions) never block. The backstop is the transcript: deciduous transcript import <session> puts the session in the graph afterwards, with each node marked proven or inferred.

"Warning: Prompt is only N chars. This looks like a summary"

The node was created. The warning asks whether the prompt is the user's message or your paraphrase of it; if it is the message, ignore it. deciduous prompt <id> replaces the text later.

A line on stderr names remote setup after every write

The project has no server anywhere, so the write stayed in the local database and the agents' MCP tools cannot see it. Run deciduous remote setup (or deciduous init), or set DECIDUOUS_QUIET_LOCAL_ONLY=1 for a project meant to stay local.

deciduous remote status exits 1

It compares content, not counts. Only here and waiting in the log: deciduous remote push. Only on the server: deciduous remote pull. Different with "edited here since the last pull": remote push --repair. Ops the server refused are listed with the reason; --drop-rejected, --drop <op> or --retry-rejected settle them.

A node written by the agent is not in deciduous nodes

With a [remote], MCP writes land on the server and reach the local cache only on deciduous remote pull. The agent's tools and the CLI read the same graph after that.

deciduous sync --check exits 1

In a project without a [remote]: records are pending in one direction or the other, edges are waiting for an endpoint, or .deciduous/graph.json cannot be read. Run deciduous sync; commit .deciduous/graph.json by path (never git add -A). A file left with conflict markers by a clone without the merge driver is repaired by sync.

Orphans

Every node except a root goal should have a parent. deciduous pulse lists coverage gaps; the MCP tools find_orphans (both servers) and, on the shared server, consolidation_report list parentless nodes with suggested parents, never linked for you. Then deciduous link PARENT ORPHAN -r "...".

Two deciduous binaries

which -a deciduous. A Homebrew install and a cargo install can both be on PATH; the first one runs. A slash command file that reaches a machine whose binary predates the subcommand (for example demo-swarm, added in 1.0.4) gets clap's unrecognized subcommand.
