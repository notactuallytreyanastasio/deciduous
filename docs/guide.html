CLI Commands Reference

Core Commands

Command Description
deciduous init Initialize deciduous in current directory (creates .deciduous/, .claude/, CLAUDE.md)
deciduous add <type> "title" Add a node (goal, decision, option, action, outcome, observation)
deciduous link <from> <to> Create edge between nodes
deciduous nodes List all nodes (filter with --branch, --type)
deciduous edges List all edges
deciduous graph Export full graph as JSON

Metadata Flags

Flag Description
-c, --confidence <0-100> Confidence level for this node
-p, --prompt "..." Store the user prompt (short, single-line)
--prompt-stdin Read prompt from stdin (multi-line, preferred for verbatim capture)
-f, --files "a.rs,b.rs" Associate files with this node
-b, --branch <name> Git branch (auto-detected by default)
--commit <hash|HEAD> Link to a git commit

Viewing & Export

Command Description
deciduous serve Start web viewer (default port 3000)
deciduous tui Start terminal UI
deciduous sync Export graph to docs/ for GitHub Pages
deciduous dot --png Generate DOT/PNG visualization
deciduous writeup Generate PR writeup markdown

Multi-User Sync

Command Description
deciduous diff export -o file.json Export nodes as a shareable patch
deciduous diff apply file.json Apply patches (idempotent)
deciduous diff status List available patches

Node Types

goal Goal

High-level objective or feature request. Root nodes in the graph.

Example: "Add user authentication to the app"

decision Decision

A choice point where you need to pick between approaches.

Example: "Choose authentication method"

option Option

A possible approach for a decision. Always linked to a decision.

Example: "Use JWT tokens", "Use session cookies"

action Action

Something you're implementing. Log BEFORE you write code.

Example: "Implementing JWT middleware"

outcome Outcome

Result of an action - success or failure. Log AFTER completion.

Example: "JWT authentication working", "Build failed due to type errors"

observation Observation

Something noticed during work - a finding, data point, or insight.

Example: "Existing code uses sessions, not JWT"

Edge Types

Type Meaning Usage
leads_to Natural progression goal -> action, action -> outcome
chosen Selected option decision -> option (the one picked)
rejected Not selected decision -> option (with reason why)
requires Dependency action -> prerequisite action
blocks Preventing progress blocker -> blocked item
enables Makes possible action -> now-possible action

Usage Patterns

Pattern 1: Logging Work in Real-Time

The core workflow for using deciduous with Claude Code:

# 1. User makes a request - create goal with verbatim prompt
deciduous add goal "Add dark mode" -c 90 --prompt-stdin << 'EOF'
I need dark mode for my app. Users should be able to toggle
between light and dark themes, and it should remember their
preference.
EOF

# 2. Before writing code - log the action
deciduous add action "Adding theme toggle component" -c 85 -f "src/ThemeToggle.tsx"
deciduous link 1 2 -r "Implementation step"

# 3. After git commit - log outcome and link
git commit -m "feat: add theme toggle"
deciduous add outcome "Theme toggle working" -c 95 --commit HEAD
deciduous link 2 3 -r "Implementation complete"

# 4. Sync for live viewing
deciduous sync

Pattern 2: Making Decisions

When choosing between approaches:

# Create the decision
deciduous add decision "Choose state management approach" -c 70

# Add options
deciduous add option "Use Redux" -c 60
deciduous add option "Use React Context" -c 75
deciduous add option "Use Zustand" -c 80

# Link options to decision
deciduous link 10 11 -r "Option A"
deciduous link 10 12 -r "Option B"
deciduous link 10 13 -r "Option C"

# After deciding, mark chosen/rejected
deciduous link 10 13 -r "Chosen: simpler API, less boilerplate" -t chosen
deciduous link 10 11 -r "Rejected: too much boilerplate" -t rejected
deciduous link 10 12 -r "Rejected: context re-renders" -t rejected

Pattern 3: Querying the Graph

Learning from past decisions:

# See all nodes
deciduous nodes

# Filter by type
deciduous nodes --type decision
deciduous nodes --type outcome

# Filter by branch
deciduous nodes --branch feature-auth

# See connections
deciduous edges

# Export for analysis
deciduous graph > graph.json

Pattern 4: Session Recovery

Starting a new session after context loss:

# What decisions exist?
deciduous nodes

# How are they connected?
deciduous edges

# What happened recently?
deciduous commands

# Check git state
git status
git log --oneline -10

Pattern 5: Team Collaboration

Sharing decisions with teammates:

# Export your work as a patch
deciduous diff export --branch my-feature -o .deciduous/patches/my-feature.json

# Commit the patch (NOT the database)
git add .deciduous/patches/
git commit -m "docs: add decision patch for feature"

# Teammate applies your patch
deciduous diff apply .deciduous/patches/my-feature.json

# Patches are idempotent - safe to re-apply
deciduous diff apply .deciduous/patches/*.json

Interactive Exercise: Building a Todo App

This exercise walks through a real development scenario, showing how the todo list expands as work progresses and new requirements emerge.

Exercise: Build a Todo List Feature

Imagine you're asked to add a todo list feature to an existing app. Here's how the work evolves:

Phase 1: Initial Request ▶

User says: "Add a todo list to the app"

1 Create goal node 
deciduous add goal "Add todo list feature" -c 90 --prompt-stdin << 'EOF'
Add a todo list to the app
EOF

Output: Created node 1 (type: goal)

Initial todo list:

  • [ ] Add basic todo list UI
Phase 2: Breaking Down the Work ▶

You realize "todo list" is vague. You need to make decisions:

2 Create decision node 
deciduous add decision "Choose todo storage approach" -c 75
deciduous link 1 2 -r "Need to decide storage"
3 Add options 
deciduous add option "LocalStorage only" -c 60
deciduous add option "Backend API with database" -c 80
deciduous link 2 3 -r "Option: simple"
deciduous link 2 4 -r "Option: persistent"

Expanded todo list:

  • [ ] Decide on storage approach
  • [ ] Add basic todo list UI
  • [ ] Implement storage layer
Phase 3: Making a Decision ▶

You choose backend API for persistence across devices:

4 Mark decision 
deciduous link 2 4 -r "Chosen: need cross-device sync" -t chosen
deciduous link 2 3 -r "Rejected: no persistence across devices" -t rejected
5 Log observation 
deciduous add observation "Existing API uses REST, should follow pattern" -c 85
deciduous link 1 5 -r "Architecture observation"

Expanded todo list:

  • [x] Decide on storage approach (Backend API)
  • [ ] Create database schema for todos
  • [ ] Implement REST endpoints
  • [ ] Add basic todo list UI
  • [ ] Connect UI to API
Phase 4: Implementation ▶

Now you implement, logging actions before code:

6 Before writing schema 
deciduous add action "Creating todos database table" -c 85 -f "migrations/001_todos.sql"
deciduous link 1 6 -r "Database setup"
7 After commit 
git add migrations/
git commit -m "feat: add todos table schema"

deciduous add outcome "Todos table created" -c 95 --commit HEAD
deciduous link 6 7 -r "Complete"

Expanded todo list (new requirements discovered!):

  • [x] Decide on storage approach (Backend API)
  • [x] Create database schema for todos
  • [ ] Implement REST endpoints
  • [ ] Add basic todo list UI
  • [ ] Connect UI to API
  • [ ] NEW: Add due dates to todos
  • [ ] NEW: Add priority levels
Phase 5: Scope Creep (User Adds Requirements) ▶

User says: "Actually, can todos have categories too?"

8 New goal for scope change 
deciduous add goal "Add categories to todos" -c 85 --prompt-stdin << 'EOF'
Actually, can todos have categories too?
EOF
deciduous link 1 8 -r "Scope expansion"
9 Decision needed 
deciduous add decision "Category implementation approach" -c 70
deciduous link 8 9 -r "Need to decide"

deciduous add option "Free-text tags" -c 65
deciduous add option "Predefined categories" -c 75
deciduous link 9 10 -r "Flexible but messy"
deciduous link 9 11 -r "Structured but limited"

Final expanded todo list:

  • [x] Decide on storage approach (Backend API)
  • [x] Create database schema for todos
  • [ ] Implement REST endpoints
  • [ ] Add basic todo list UI
  • [ ] Connect UI to API
  • [ ] Add due dates to todos
  • [ ] Add priority levels
  • [ ] NEW: Decide category approach
  • [ ] NEW: Implement categories
  • [ ] NEW: Add category filter UI
Key Insight: The decision graph captures WHY the todo list expanded - the user's request is preserved verbatim, decisions are documented, and you can trace how "add a todo list" became 10 tasks.

Enforcement Hooks

Deciduous includes Claude Code hooks that enforce decision logging. These are installed automatically with deciduous init or deciduous update.

PreToolUse Hook: Require Action Node

Blocks Edit/Write tools if no recent action or goal node exists (within 15 minutes).

If you see this error:
DECIDUOUS: No recent action/goal node found

Run one of these before editing: 
deciduous add goal "What you're trying to achieve" -c 90
# or
deciduous add action "What you're about to implement" -c 85

PostToolUse Hook: Commit Reminder

After every git commit, reminds you to link it to the decision graph.

After committing, run: 
deciduous add outcome "What was accomplished" -c 95 --commit HEAD
deciduous link <action_id> <outcome_id> -r "Implementation complete"

/work Skill

Use the /work slash command to start a transaction:

/work "Add user authentication"

This creates the goal node automatically, capturing the user's request.
