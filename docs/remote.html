One Graph, Every Project

One Postgres server holds every repository's decision graph, one workspace each — queryable alone or all at once. The server is the truth; your local database becomes a cache of it.

Why a server

Agents write through the HTTP MCP server, so a project with no server is a project whose agents have nowhere to write. Every project points at one, and deciduous init does not finish until the project points at one that answers.

The server does not have to be somewhere else. By default it runs on this machine, as a background service installed under ~/.config/deciduous/server/ (a launchd LaunchAgent on macOS, a systemd user unit on Linux), and keeps its data in a PostgreSQL on localhost:5432, connecting as the current OS user to a database called deciduous that it creates and migrates itself. That is the PostgreSQL a brew install postgresql@17 or a distribution package already runs. If nothing answers on 5432, init says so in the menu and prints what to do:

when nothing answers on localhost:5432
Nothing answers on localhost:5432, so choice 1 needs a PostgreSQL first:
macOS: brew install postgresql@17 && brew services start postgresql@17
Debian/Ubuntu: sudo apt install postgresql
Or name another PostgreSQL (choice 2, --database-url), or let Docker run one
for you (choice 3, --docker-postgres).

Any other PostgreSQL works if you give its URL. Docker can run both PostgreSQL and the server, if you would rather install neither. A team can run one server on a shared machine and hand out its URL and token; that runbook is deciduous_mcp/DEPLOY.md, and the projects that use it take choice 4 below.

Wherever it runs, every repository gets its own workspace, and one query can cross all of them. “What did I decide about auth, across every project I've touched?” has an answer because the data is in one place.

Two writable stores. Once a project has a remote, the CLI (deciduous add) and any MCP client (add_node) can both write. The CLI writes locally and queues an op that is sent to the server before the command exits; an MCP write never reaches the local database until pull. Treat the server as the source of truth and the local database as a cache you refresh with pull, not a second copy you edit independently; deciduous remote status reports the gap.

Setting up a repository

deciduous init (and deciduous update) in a project whose .deciduous/config.toml has no [remote] asks, in a terminal, where the project's graph should live:

deciduous init, the server step
$ deciduous init
...
Shared graph server
This project has no server yet ([remote] in .deciduous/config.toml).
Where should this project's graph live?
1) This machine: the deciduous server as a background service, using PostgreSQL on
localhost:5432 as you (answering now)
2) This machine: the server as a background service, using a PostgreSQL you name
(any host, port, user, password)
3) This machine, in Docker: a new PostgreSQL and the server in containers
4) A server someone else runs: you need its URL and token
1 and 2 install the release's server executable in /Users/you/.config/deciduous/server
and start it at login. --docker runs that server in Docker instead.
Choose 1-4 [1]:
  • 1, the default. The first time on a machine, init downloads the server executable for its own version (one file with Erlang and Elixir inside), checks it against the release's checksums.txt, and runs it once to create the database deciduous and apply migrations. If PostgreSQL refuses (no such role, wrong password, no CREATEDB), you see its reason and the menu again. Then it installs the server as a user service that starts at login. It listens on 127.0.0.1 only.
  • 2. The same server, against a PostgreSQL you name: postgres://USER@HOST:PORT/DATABASE, with ?sslmode=require or verify-full for TLS. The password is asked separately and not shown.
  • 3. Downloads the Docker bundle for its own version, checks it, and starts PostgreSQL 17 and the server in containers (a few minutes the first time). This is what 1.0.10 and earlier always did; an existing Docker install stays as it is.
  • 4. Asks for the URL and the token (typed without being shown), and checks both against the server before storing anything.

For 1 to 3 the server needs a port on this machine, and init asks for it with a free one suggested from 20000-32767. The port is asked rather than fixed so that the server never squats one the machine already wants:

The Claude Code registration is this, run for you:

If claude is not on PATH, setup prints Claude Code not found; register the server in your client: <url>/mcp and the line above is what to run, or what to translate for another MCP client.

The second project on this machine

Every later deciduous init finds the server that is already running, in about a second, and skips the installation:

deciduous init, in a second project
Found local server at http://127.0.0.1:24871
Wrote .deciduous/config.toml [remote] url = http://127.0.0.1:24871
Connected http://127.0.0.1:24871 holds 0 nodes, 0 edges in workspace other-project
Unchanged Claude Code already has a deciduous MCP server

deciduous remote setup asks the same question on its own, in a project that already has [remote] too (it offers to keep the current server first). Once this machine has a server, the menu shrinks to two choices: that server, or one someone else runs. deciduous update also upgrades this machine's server executable when it is older than the CLI.

In a script

There is no terminal to ask, so give the answer instead; without one init stops and prints these:

deciduous remote setup, scripted
$ deciduous remote setup --local # this machine: a background service, PostgreSQL on localhost:5432
$ deciduous remote setup --database-url <url> # this machine's server, a PostgreSQL you name
$ deciduous remote setup --docker-postgres # this machine: PostgreSQL and the server in Docker
$ deciduous remote setup --url <url> # a server someone else runs

--docker runs this machine's server in Docker against the PostgreSQL from --local or --database-url. --port <n> or DECIDUOUS_PORT answers the port question the first time; after that the port in ~/.config/deciduous/server/.env stands. --url takes its token from DECIDUOUS_MCP_TOKEN or the stored one. DATABASE_URL in your environment is never used unless you pass it with --database-url. Tests and CI in a throwaway directory set DECIDUOUS_NO_SERVER=1 to skip the step.

The lower-level commands

Setup is built from three commands that still work on their own.

deciduous remote login stores a token by hand. It reads from stdin so the token never lands in shell history or the process list, and with --url it checks the token against that server before storing anything:

deciduous remote login
$ deciduous remote login --url https://example.com/deciduous-mcp
Token (read from stdin, not saved to shell history):
Token: stored in /Users/you/.config/deciduous/credentials
mode 0600, outside every repository

deciduous remote init <url> points one repository at a server whose token is already stored or in the environment. It verifies the server answers and claims the workspace before writing; if either fails it says which and leaves the project untouched. Then it sends the server the local history it lacks:

deciduous remote init
$ deciduous remote init https://example.com/deciduous-mcp
Remote: https://example.com/deciduous-mcp
workspace: blog
claim: verified (by this repository's root commit)
server holds 719 nodes, 845 edges, 0 documents
sent 12 local node(s), 9 edge(s) the server lacked
Written to .deciduous/config.toml. The token stays in ~/.config/deciduous/credentials (or DECIDUOUS_MCP_TOKEN), never here.

The workspace name is the git repository root's directory name, lowercased, not the current directory, so running the CLI from a subdirectory can't split one project across two workspaces. Override it if the directory name isn't what the graph should be called:

custom workspace name
$ deciduous remote init https://example.com/deciduous-mcp --workspace my-project

Configure many projects at once

adopt walks a directory for projects that already have a .deciduous, and points each at the server. It never repoints a project already aimed somewhere else — that moves where its decisions land, and is not a bulk operation's call. Dry-run first if you have a lot of repositories:

deciduous remote adopt
$ deciduous remote adopt ~/code --url https://example.com/deciduous-mcp --dry-run
Would configure: 91 projects under /Users/you/code
blog already configured
scratch (some-experiment) would configure
my-app would configure
...
90 would be configured, 1 left alone
$ deciduous remote adopt ~/code --url https://example.com/deciduous-mcp
90 configured, 1 left alone

Several directories can share one workspace name: anything outside a git repository pools into scratch rather than minting a workspace per temporary directory, so adopt prints the directory alongside the workspace whenever they'd otherwise be indistinguishable.

Checking for drift

status compares content, not counts: what is waiting in the log, and every node, edge and document that differs, field by field, each with the command that fixes it. It exits 1 when anything differs.

deciduous remote status, in sync
$ deciduous remote status
Remote: http://127.0.0.1:24871
Workspace: blog
Log: 0 write(s) waiting, 0 rejected (.deciduous/remote-log.jsonl)
local server
nodes 719 719
edges 845 845
In sync: no writes waiting, and every node, edge and document matches field by field.
Themes and tags are not sent to the server, so they are not compared.

Two graphs can hold the same number of nodes and different nodes, which is why the table is not the verdict. When they differ, each side's extra rows are listed by name:

drift, in both directions at once
Log: 1 write(s) waiting, 0 rejected (.deciduous/remote-log.jsonl)
waiting b220f13c create goal 6645c7fc "bobs unpushed goal"
local server
nodes 2 2
edges 0 0
Only here (1)
goal 6645c7fc "bobs unpushed goal" (waiting in the log)
Only on the server (1)
goal 0e355b0b "agents goal"
Differs: `deciduous remote push` sends what is waiting and what this machine set aside; `deciduous remote pull` takes the server's side.

A node listed under Different says which fields differ and which side edited it later: status: here completed, server pending (edited here since the last pull: `deciduous remote push --repair` sends it). When this copy did, the edit's op never reached the log; it may have been made before this clone's config had a [remote], or while the log could not be written. A node an agent deleted is listed under Deleted on the server, and remote pull removes it here; --seed never sends it back. Ops the server refused are listed with the start of their op id and the reason, until remote push --drop-rejected, --drop <op id> or --retry-rejected.

Pull and push

pull is the normal way to refresh — it fetches the server's graph and merges it into the local cache through the same reconcile logic deciduous sync already uses between machines: newer updated_at wins, deletes are tombstones, an edge waits until both endpoints exist locally.

a node written via MCP, pulled into local SQLite
$ deciduous remote status
local server
nodes 2 3
edges 1 1
Only on the server (1)
observation 68701826 "Written remotely, never seen locally"
Differs: `deciduous remote pull` takes the server's side.
$ deciduous remote pull
Pulled: roundtrip <- http://127.0.0.1:24871
fetched 3 nodes, 1 edges, 0 deletion(s)
imported 1 new node(s), updated 0, removed 0; imported 0 edge(s), removed 0
$ deciduous nodes
3 68701826 observation pending Written remotely, never seen locally

push is not the normal write path — routine writes should go through MCP or the CLI's own add, which writes locally and reaches the server through the log before the command exits. push exists to seed a new workspace, or to carry history that predates the server:

seeding a workspace
$ deciduous remote push
Pushed: roundtrip -> http://127.0.0.1:24871
nodes 2 of 2
edges 1 of 1

Asking across every project

Read tools accept workspace: "*", over MCP, for the cross-project view:

CallResult
query_nodes workspace="blog"just that repository
query_nodes workspace="*"every repository, each node tagged with its own
list_workspacesthe index — what exists, how big, when it last changed

Writes refuse the global token, because a node has to land somewhere specific:

add_node workspace="*"
{"code": -32000, "message": "workspace \"*\" is read-only: a node must be written to one project. Pass the repo name."}

Pinning a repository

Setup registers the server with Claude Code at user scope, which is all one machine needs. A repository that wants its workspace unambiguous — regardless of what any tool call says — adds a .mcp.json with a header. The header beats the workspace argument, on reads and writes alike, and a pinned repository ignores workspace: "*" on reads too: a project that opted into isolation can't be made to read its neighbours.

.mcp.json

{
  "mcpServers": {
    "deciduous": {
      "type": "http",
      "url": "https://example.com/deciduous-mcp/mcp",
      "headers": {
        "Authorization": "Bearer ${DECIDUOUS_MCP_TOKEN}",
        "X-Deciduous-Workspace": "my-project"
      }
    }
  }
}
Use ${DECIDUOUS_MCP_TOKEN}, never a literal token. .mcp.json is a file people commit — that's how a team shares server config — and Claude Code expands ${VAR} from the environment when it connects. With the variable unset it refuses and says so: Missing environment variables: DECIDUOUS_MCP_TOKEN. A literal token here is a credential committed to your repository.

Working alongside other agents

Two sessions writing to one workspace need to know the other exists and to find out when it writes. The branch is the unit for both.

No locks: every write is recorded, none is refused

Until 1.0.8 every write claimed an advisory lock on (workspace, branch) with a ten-second lease, and a second session on the branch was refused with the holder's name. It stopped the writer it should never stop and could not stop the other one:

  • A one-shot client (initialize, one call, exit) left its lease behind, and its own next process was refused for ten seconds: locked by battery (0), session GNgCXo-N. A server cannot tell that a session's process is gone.
  • The CLI took no lock: its writes are replayed from .deciduous/remote-log.jsonl through POST /ops, possibly days after they were made.

And nothing needs the exclusion. Every write is atomic on its own: a node insert, an update read FOR UPDATE, capture_conversation_turn and log_decision in one transaction each, /ops compare-and-set field by field. Two agents on one branch interleave their nodes, as two people on one branch do, and no write is lost or torn.

So a write now records who wrote where: workspace, branch, session and clientInfo for MCP; deciduous CLI and the repository's root commit for /ops. It never refuses. Pass branch on every write so the record says which one. The workspace setting lock_scope no longer does anything.

check_activity

The read side. Call it before a burst of writes, and after every milestone, instead of polling query_nodes.

FieldWhat it holds
sessionsevery session, MCP or CLI, that wrote in the last five minutes (window_seconds): branch, client, client_version, session, is_you, first_seen_at, last_seen_at, seconds_ago
active_sessionshow many distinct sessions that is
branchesthe twenty most recently written branches: each with last_node (id, change_id, node_type, title, status, created_at) and writers, the sessions above that wrote it. Pass branches: N for more; branches_total says how many the workspace has in all

It used to list unexpired locks, which had always lapsed by the time anyone looked, so a run of short-lived clients read active_sessions: 0 throughout, and CLI writes, which took no lock, never appeared at all.

Events

Postgres triggers call pg_notify on every insert or update to decision_nodes and every insert to decision_edges. One listener bridges that to a WebSocket at GET /events, scoped to a workspace or to "*" for all of them. A frame is a pointer with enough text to quote, not the row:

one frame

{"table":"decision_nodes","op":"INSERT","workspace":"tetris-arena",
 "id":"…","change_id":"8d2f482a-…","node_type":"observation","status":"pending",
 "branch":"agent-7",
 "title":"Took the step-reset for lock delay from agent-8's decision, …"}

Edge frames carry edge_type, both endpoints' change_id, and the branch of the source node. Edges have no branch of their own; before 1.0 a watcher could not tell whose edge it was looking at.

The handshake cannot carry an Authorization header from a browser WebSocket or anything built on one, so ?token= is accepted as a fallback. It is a bearer token in a URL: do not paste it anywhere that logs.

deciduous remote watch

Connects to that socket for the current repository's workspace and prints one line per write. It quotes; it does not count. It reconnects with backoff when the socket closes.

Why quote rather than count. During the arena a session watching the raw stream kept a per-branch tally and reported that a "second goal" convention was spreading through the agents. The graph had ten goals, one per agent; the tally had counted updates as inserts. A line that quotes the title and the operation cannot invent that.

The message board

Agents working at the same time coordinate through post_message and read_messages (server 1.0.9), or deciduous board post|read|show, which in a project with a [remote] go to POST and GET /messages with the same token and workspace as /export. @label addresses a message, reply_to answers one, and read_messages with unanswered_for your label is your inbox. An older server answers 404, and the CLI says which version it needs instead of writing to the local table, where no other agent would look. deciduous remote watch prints each post: message #18 re #16 board-server -> board-cli "choices".

took_from

An edge type for a borrow. from is the node you took from, to is your node that used it, and it crosses branches on purpose. log_observation takes took_from (a node UUID or a full change_id) and why (the edge's rationale) and writes the observation and the edge in one call; add_edge and deciduous link -t took_from take it directly.

log_observation

log_observation({
  workspace: "tetris-arena", branch: "agent-7",
  title: "Took the step-reset for lock delay from agent-8's decision",
  took_from: "767cce30-9d0b-4e56-a4d8-2f0b1c8e7a11",
  why: "Resetting the lock timer on every step is what makes fast play at the floor feel fair.",
  description: "agent-8's game.js did not have it coded yet when I read it, so this implements the idea from the graph rather than from code."
})

In the arena zero of 471 edges crossed a branch. The agents cited each other in 89 of 91 observation titles, four of them by change_id, and never linked to the node, because the rules said to link every node to its parent and did not say the node you borrowed from counts. The borrow figures in the write-up come from a regular expression over titles. That is the wrong place for that information to live; took_from is the right one.

Running the server

The server is an Elixir app (deciduous_mcp/ in the repository) backed by PostgreSQL, with an MCP endpoint over Streamable HTTP. Documents are stored in PostgreSQL too, keyed by content hash, so a file attached to more than one project's graph is stored once. On your own machine, setup installs and runs it; there is nothing else to do.

For a team, one server on a shared machine behind a reverse proxy, with one URL and token handed out and every project taking choice 4: see deciduous_mcp/DEPLOY.md in the repository for the runbook, the native executable and the Docker Compose service alike.

What this doesn't do

  • Themes don't transfer. The graph export used to move data to the server doesn't carry theme assignments yet, so they stay local to each repository's SQLite.
  • push isn't the normal write path. It exists to seed a workspace and to carry history that predates the server.
  • MCP writes do not come back on their own. A CLI write made while the server is down waits in .deciduous/remote-log.jsonl and goes on the next write or deciduous remote push; a node an agent wrote through MCP reaches the local cache only on deciduous remote pull.
  • Self-loop edges are rejected by the server's schema, and reported per project rather than silently dropped.
  • A session that outlives the server is refused, not resumed. Sessions expire after 24 idle hours, and a restart drops all of them. The next call on an old mcp-session-id gets 404 with JSON-RPC error -32001 Session not found under the request's own id, and the client starts a new session. Before 1.0 the server answered such a call with a 200 under a made-up id, and Claude Code waited 300 seconds for a reply it could never match, on every call, until the process was restarted.
  • The event stream is advisory. Postgres does not queue a NOTIFY that fires while the listener's connection is down, and a reconnect races new LISTENs against notifications issued at the same moment. A gap in the stream is not proof that nothing happened; a subscriber that needs certainty calls check_activity or query_nodes to catch up.
  • Activity is a record, not a lock. Two sessions can write one branch at once; check_activity is how each learns of the other.
  • A document can outlive its bytes. If a file referenced by a document row is missing at import time, the row still imports as history and a fetch answers 410 Gone rather than 404 — the attachment was real; the bytes are gone.
